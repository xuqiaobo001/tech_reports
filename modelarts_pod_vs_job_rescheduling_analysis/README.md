# 华为云 ModelArts Pod 重调度 vs 隔离式 Job 重调度深度对比分析

> 基于华为云 ModelArts 官方文档，深入分析 Pod 重调度与隔离式 Job 重调度两种故障恢复策略的设计意图、适用场景、降级关系，以及为什么两者都处理节点故障。

---

## 一、问题背景

ModelArts 训练作业故障恢复体系中有两种策略都声称处理"节点故障"：

| 策略 | 触发场景（官方文档） |
|------|---------------------|
| **Pod 重调度** | NPU 芯片故障 / 节点故障 |
| **隔离式 Job 重调度** | NPU 芯片故障 / 节点故障 |

一个自然的疑问是：**既然 Pod 重调度已经能处理节点故障（只重建故障 Pod，保留正常 Pod），为什么还需要隔离式 Job 重调度来做同样的事？**

答案的核心在于：**绝大多数分布式训练框架不支持运行中动态替换成员**。

---

## 二、两种策略的架构差异

### 2.1 可视化对比

```
================== Pod 重调度 ==================

  Job 实例（保留不变）
  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
  │Pod-0│  │Pod-1│  │Pod-2│  │Pod-3│
  │ 正常 │  │ 正常 │  │ ✗故障│  │ 正常 │
  └──┬──┘  └──┬──┘  └─────┘  └──┬──┘
     │        │      ↓重建       │
     │        │  ┌─────┐        │
     │        │  │Pod-2│        │
     │        │  │(新) │        │
     └────────┴──┴──┬──┴────────┘
                     │
     正常 Pod 的容器环境、内存数据全部保留
     不重新初始化，不重新下载数据

================== 隔离式 Job 重调度 ==================

  旧 Job 实例 → 全部销毁
  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
  │Pod-0│  │Pod-1│  │Pod-2│  │Pod-3│   全部 ×
  └─────┘  └─────┘  └─────┘  └─────┘

           ↓ 隔离故障节点 + 完全重建

  新 Job 实例（全新创建）
  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
  │Pod-0│  │Pod-1│  │Pod-2│  │Pod-3│   全部新建
  │(新) │  │(新) │  │(新) │  │(新) │
  └─────┘  └─────┘  └─────┘  └─────┘

  所有 Pod 从零初始化
  重新建立通信拓扑、重新下载/加载数据
```

### 2.2 策略特性对比

| 维度 | Pod 重调度 | 隔离式 Job 重调度 |
|------|-----------|-----------------|
| **恢复粒度** | 单个 Pod | 整个 Job（所有 Pod） |
| **正常 Pod** | 保留，继续运行 | 全部销毁并重建 |
| **容器环境** | 故障 Pod 的容器被替换 | 所有容器全部重建 |
| **内存数据** | 正常 Pod 内存数据保留 | 全部丢失，从 CKPT 恢复 |
| **通信拓扑** | 需要动态重建（部分） | 完全重新初始化 |
| **恢复速度** | 快（只重建一个 Pod） | 慢（全部重建） |
| **资源需求** | 需要健康备用机 | 需要健康备用机 |
| **脚本要求** | 可重入（跳过数据下载等） | 可重入（从 CKPT 恢复） |
| **占用重启次数** | 是 | 是 |

## 三、为什么 Pod 重调度在大多数场景下不可行

### 3.1 分布式训练的静态拓扑问题

主流分布式训练框架（PyTorch DDP、DeepSpeed、Megatron-LM、MindSpore 等）在训练启动时确定通信拓扑，运行中 **不能动态变更成员**：

```
训练启动时建立的通信组（以 PyTorch DDP 为例）：

  world_size = 4
  后端 = NCCL / HCCL

  Pod-0 (rank=0) ←→ Pod-1 (rank=1) ←→ Pod-2 (rank=2) ←→ Pod-3 (rank=3)
       ↑                 ↑                  ↑                   ↑
    正常运行           正常运行            节点宕机             正常运行
```

### 3.2 Pod 替换后的死锁场景

```
当 Pod-2 所在节点故障后，尝试 Pod 重调度：

Step 1: Pod-2 被销毁，在新节点上创建新 Pod-2'
  ┌─────┐  ┌─────┐              ┌─────┐
  │Pod-0│  │Pod-1│    新 Pod     │Pod-3│
  │rank0│  │rank1│  ┌─────┐     │rank3│
  │ 正常 │  │ 正常 │  │Pod-2'│    │ 正常 │
  └──┬──┘  └──┬──┘  │rank2│     └──┬──┘
     │        │     └──┬──┘        │
     │        │        │           │
     │        │        │           │

Step 2: 但 Pod-0/1/3 仍持有旧的 NCCL/HCCL 通信组
     → 它们在等待 rank=2 的旧进程响应
       （AllReduce 等 group 操作需要所有 rank 参与）
     → 永远等不到，因为旧进程已死

Step 3: 新 Pod-2' 尝试加入通信组
     → NCCL/HCCL 的 world_size 和 rank_table
       在初始化时就固定了（静态配置）
     → 新 Pod 无法加入已建立的通信组

Step 4: 结果 → 死锁
     Pod-0/1/3 等待旧 rank=2 → 永远不会来
     Pod-2' 尝试初始化新通信组 → 无法与旧组协调
```

### 3.3 根本原因

| 问题 | 说明 |
|------|------|
| **静态 world_size** | NCCL/HCCL 通信组在初始化时确定 world_size，运行中不能改变 |
| **静态 rank 分配** | 每个 Pod 的 rank 在启动时分配，新 Pod 无法获取原 rank 的通信上下文 |
| **集合通信阻塞** | AllReduce/AllGather 等操作需要所有 rank 参与，缺一个就死锁 |
| **进程组不可变** | PyTorch 的 ProcessGroup 创建后不可修改成员 |

## 四、两种策略的实际定位

### 4.1 设计意图对比

```
Pod 重调度（理想方案）
  ├─ 设计目标：最小化恢复开销，只替换故障部分
  ├─ 前提条件：训练框架支持动态成员替换
  ├─ 适用框架：TensorFlow PS 模式、Ray 等支持动态拓扑的框架
  └─ 实际情况：大多数主流训练框架不支持 → 经常失败

隔离式 Job 重调度（现实方案/通用兜底）
  ├─ 设计目标：确保在任何框架下都能恢复训练
  ├─ 前提条件：无特殊要求，只需代码支持断点续训
  ├─ 适用框架：所有框架（PyTorch/DeepSpeed/Megatron/MindSpore 等）
  └─ 实际情况：最常用的恢复手段
```

### 4.2 各框架对 Pod 替换的支持情况

| 训练框架 | 是否支持动态成员替换 | 推荐策略 |
|----------|---------------------|---------|
| **PyTorch DDP** | 不支持（静态 ProcessGroup） | 隔离式 Job 重调度 |
| **DeepSpeed ZeRO** | 不支持（依赖 NCCL 静态拓扑） | 隔离式 Job 重调度 |
| **Megatron-LM** | 不支持（张量并行+流水线并行静态拓扑） | 隔离式 Job 重调度 |
| **MindSpore** | 不支持（静态 RankTable） | 隔离式 Job 重调度 |
| **TensorFlow PS 模式** | 部分支持（Worker 可替换） | 可尝试 Pod 重调度 |
| **Ray Train** | 支持（原生 Actor 替换） | Pod 重调度优先 |
| **Horovod** | 不支持（静态 MPI 通信组） | 隔离式 Job 重调度 |

## 五、降级关系与策略选择

### 5.1 完整的降级链路

```
故障发生
  │
  ├─ 可自愈芯片故障？ → ① 原地恢复
  │    ├─ 自愈成功 → 恢复训练
  │    ├─ 自愈失败 → 降级
  │    │    ├─ 非用户输入引发 → 尝试 Pod 重调度
  │    │    │    ├─ 成功 → 恢复训练
  │    │    │    └─ 失败 → 节点已隔离 → ⑤ 无条件 Job 重调度
  │    │    └─ 用户输入引发 → ⑤ 无条件 Job 重调度（不隔离节点）
  │    └─ 24h 同芯片 3 次 → ④ 隔离式 Job 重调度
  │
  ├─ 不可自愈芯片/节点故障？
  │    ├─ 开启了 Pod 重调度？ → 尝试 ③ Pod 重调度
  │    │    ├─ 成功 → 恢复训练（极少数场景）
  │    │    └─ 失败 → 节点已隔离 → ⑤ 无条件 Job 重调度
  │    └─ 未开启 Pod 重调度 → ④ 隔离式 Job 重调度
  │
  └─ 软件故障（退出码≠0）？ → ⑤ 无条件 Job 重调度
       ├─ 连续 ≤3 次 → 重建 Job
       └─ 连续第 4 次 → 作业失败
```

### 5.2 为什么 Pod 重调度失败后降级到"无条件"而非"隔离式"？

> 因为 Pod 重调度在执行时**已经完成了节点隔离**。降级时节点已隔离完毕，直接走无条件 Job 重调度即可（不需要重复隔离）。

```
Pod 重调度失败后的降级：

  1. Pod 重调度执行
     ├─ 已隔离故障节点 ✓
     ├─ 尝试仅重建故障 Pod
     └─ 重建失败（如通信拓扑无法重建）

  2. 此时节点已隔离，无需再隔离
     └─ 直接走"无条件 Job 重调度"重建整个 Job
        （跳过了隔离步骤，因为已经做过了）
```

## 六、配置建议

### 6.1 通用推荐配置

| 配置项 | 推荐值 | 原因 |
|--------|--------|------|
| 自动重启（含原地恢复+隔离式Job重调度） | 开启，8~128次 | 覆盖大多数故障场景 |
| 无条件自动重启 | 开启 | 兜底软件/网络故障 |
| 作业卡死重启 | 开启 | 覆盖卡死场景 |
| Pod 重调度 | 开启，3次 | 少数框架下可快速恢复，失败自动降级 |

### 6.2 按场景配置

| 场景 | 推荐策略组合 | 说明 |
|------|-------------|------|
| PyTorch DDP 大模型训练 | 自动重启 + 无条件重启 + 卡死重启 | Pod 重调度大概率失败，但不影响（会降级） |
| DeepSpeed/Megatron 训练 | 自动重启 + 无条件重启 + 卡死重启 | 同上 |
| TensorFlow PS 模式 | 自动重启 + Pod 重调度 + 无条件重启 | PS 模式下 Pod 重调度可能生效 |
| Ray 集群训练 | 自动重启 + Pod 重调度（优先） | Ray 原生支持动态替换 |

### 6.3 断点续训适配要点

无论哪种恢复策略，都必须确保代码支持断点续训：

```python
import os
import torch

# 利用环境变量判断恢复类型
schedule_cnt = int(os.environ.get('MA_SCHEDULE_CNT', '1'))
proc_start_cnt = int(os.environ.get('MA_PROC_START_CNT', '1'))

if schedule_cnt > 1:
    # 发生过 Job 级重调度或 Pod 重调度
    # → 需要从 CKPT 恢复，跳过数据下载
    start_epoch = load_checkpoint(model, optimizer, ckpt_path)
    skip_data_download = True
else:
    skip_data_download = False

if proc_start_cnt > 1:
    # 发生过原地恢复或卡死重启
    # → 需要重建共享内存，跳过数据预处理
    rebuild_shared_memory()
    skip_preprocessing = True
```

## 七、总结

| 问题 | 回答 |
|------|------|
| Pod 重调度和隔离式 Job 重调度有什么区别？ | Pod 重调度只替换故障 Pod（保留正常 Pod）；隔离式 Job 重调度完全重建整个 Job |
| 为什么两者都处理节点故障？ | Pod 重调度是理想方案（快速），但对大多数框架不可行；隔离式 Job 重调度是通用兜底方案 |
| Pod 重调度在什么场景下有效？ | 框架支持动态成员替换时（如 Ray、TF PS 模式） |
| 为什么 PyTorch/DeepSpeed 下 Pod 重调度无效？ | NCCL/HCCL 通信组是静态的，新 Pod 无法加入已建立的通信组，导致死锁 |
| 降级链路是什么？ | Pod 重调度失败 → 无条件 Job 重调度（节点已隔离，无需再隔离） |
| 应该怎么配置？ | 两种都开启，让系统自动选择和降级。关键是确保代码支持断点续训 |
