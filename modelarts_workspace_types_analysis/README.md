# 华为云 ModelArts 工作空间三种类型深度分析

## 1. 工作空间解决的核心问题

ModelArts 工作空间解决的是**多用户/多项目场景下的资源隔离与权限管控**问题：

- **资源逻辑隔离**：将数据集、算法、训练作业、模型、在线服务等资源按空间隔离
- **配额管理**：按空间维度限制 GPU/CPU/内存使用量（训练卡数、训练时长、推理服务时长等 13 项配额）
- **细粒度鉴权**：控制谁能访问哪些空间中的资源
- **资源清理**：删除工作空间时自动清理其下所有资源
- **企业项目管理集成**：与华为云企业项目服务整合，实现按项目的成本核算

> **注意**：工作空间是**白名单功能**，需要提工单申请开通。开通后系统会默认创建一个名为 `default` 的 PUBLIC 工作空间。

## 2. 三种类型的权限差异矩阵

| 维度 | PUBLIC（公开） | PRIVATE（私有） | INTERNAL（内部） |
|------|---------------|----------------|-----------------|
| **主账号** | ✅ 完全访问 | ✅ 完全访问 | ✅ 完全访问 |
| **创建者** | ✅ 完全访问 | ✅ 完全访问 | ✅ 完全访问 |
| **所有 IAM 子账号** | ✅ 全部可见可访问 | ❌ 完全不可见 | ❌ 不可见 |
| **指定 IAM 子账号** | 不需要指定 | 不需要指定 | ✅ 可访问（grants 列表） |
| **联邦用户（SAML）** | ✅ 全部可访问 | ❌ | ✅ 可指定 |
| **委托用户** | ✅ 全部可访问 | ❌ | ✅ 可指定 |
| **API 参数** | `auth_type: "PUBLIC"` | `auth_type: "PRIVATE"` | `auth_type: "INTERNAL"` + `grants` 数组 |
| **授权用户上限** | 无（自动包含所有人） | 2 人（创建者+主账号） | 最多 500 人 |

## 3. 三种类型的典型业务场景

### 3.1 PUBLIC — 全员共享

```
租户 A
├── 主账号
├── 子账号 张三 (算法组)
├── 子账号 李四 (算法组)
├── 子账号 王五 (数据组)
└── 子账号 赵六 (运维组)

PUBLIC 工作空间 "shared-ml"
    → 所有人都能看到和使用其中的数据集、模型、训练作业
```

**适用场景：**
- 小团队快速协作，无需权限管控
- 共享公共数据集和预训练模型库
- 系统 `default` 工作空间就是 PUBLIC 类型
- 公司内部通用 AI 基础设施平台

**业务影响：**
- **优势**：零配置、全员可见，协作效率最高
- **风险**：任何人都可能误删/修改他人的训练作业或模型

### 3.2 PRIVATE — 个人隔离

```
PRIVATE 工作空间 "core-algo-v2"
    → 仅创建者 + 主账号可访问
    → 其他人完全看不到这个空间的存在
```

**适用场景：**
- 核心算法研发（如推荐算法、风控模型），防止代码/数据泄露
- POC 阶段的探索性实验，不希望影响他人
- 敏感数据（用户画像、金融数据）处理环境
- 安全合规要求高的项目（等保、数据安全法）

**业务影响：**
- **优势**：最强隔离性，仅 2 人可见
- **代价**：无法直接协作，需要通过主账号中转或完成后迁移到 PUBLIC 空间

### 3.3 INTERNAL — 精确授权

```
INTERNAL 工作空间 "recsys-production"
    grants: [张三(算法), 李四(算法), 赵六(运维)]
    → 王五（数据组）无法看到此空间
```

**适用场景：**

| 场景 | 具体做法 |
|------|----------|
| **按角色隔离** | 创建 `prod-workspace`（INTERNAL）仅授权运维人员，`dev-workspace`（INTERNAL）仅授权开发人员 |
| **教育培训** | 给每个学生创建 1 个 INTERNAL 空间，仅该学生可访问，实验互不干扰 |
| **跨部门项目** | 从算法组选 2 人 + 数据组选 1 人，授权到同一个 INTERNAL 空间 |
| **联邦用户（SAML SSO）** | 授权对象类型选择"联邦用户"，输入 IdP 侧的用户名或用户 ID |
| **委托用户** | 授权对象类型选择"委托用户"，指定委托名称（跨账号场景） |

**业务影响：**
- **优势**：最灵活，精确控制谁能访问
- **代价**：管理开销大，人员变动需及时更新 grants 列表

## 4. INTERNAL 类型的授权对象类型

INTERNAL 类型支持三种授权对象：

### 4.1 IAM 子用户

从下拉列表选择（控制台）或传入 `user_name`/`user_id`（API）。

```json
{
  "auth_type": "INTERNAL",
  "grants": [
    { "user_name": "zhangsan" },
    { "user_name": "lisi" }
  ]
}
```

### 4.2 联邦用户

手动输入联邦用户的用户名或用户 ID（来自企业 IdP）。适用于通过 SAML SSO 联邦认证登录的用户。

### 4.3 委托用户

选择委托名称，适用于跨账号访问场景（如 A 账号的用户需要访问 B 账号的 ModelArts 资源）。

## 6. 选型决策树

```
是否需要限制谁能访问？
├── 否 → PUBLIC
└── 是
    ├── 是否只需创建者+主账号？
    │   └── 是 → PRIVATE
    └── 否，需要指定特定人员
        └── INTERNAL
            ├── 授权对象 ≤ 500 人？
            │   └── 是 → 直接使用
            └── 否 → 需要拆分为多个 INTERNAL 空间
```

## 7. API 参考

### 创建工作空间

```
POST /v1/{project_id}/workspaces
```

**请求示例：**

```json
{
  "name": "test-workspace",
  "description": "It is a test project",
  "enterprise_project_id": "***b0091-887f-4839-9929-cbc884f1e***",
```

## 8. 注意事项

1. **白名单功能**：工作空间功能需要提工单申请开通
2. **default 不可删除**：系统默认的 `default` 工作空间（PUBLIC 类型）不支持删除
3. **删除不可恢复**：删除工作空间会清理其下所有资源，包括数据集、训练作业、模型等
4. **授权类型可修改**：创建后支持修改名称、描述、企业项目和授权类型（PUBLIC ↔ PRIVATE ↔ INTERNAL）
5. **与 IAM 策略互补**：工作空间权限是资源可见性级别的管控，与 IAM 细粒度策略（谁能创建/删除/修改操作）是两层独立的权限体系

## 9. 总结对比

| 对比项 | PUBLIC | PRIVATE | INTERNAL |
|--------|--------|---------|----------|
| **核心定位** | 全员共享协作 | 个人/核心项目隔离 | 精确团队授权 |
| **访问范围** | 租户下所有用户 | 仅创建者 + 主账号 | 创建者 + 主账号 + 指定用户 |
| **管理复杂度** | 最低 | 低 | 中（需维护 grants） |
| **安全等级** | 低 | 高 | 中-高 |
| **授权上限** | 无限制 | 2 人 | 500 人 |
| **典型场景** | 团队共享、公共模型库 | 核心算法研发、敏感数据 | 跨部门项目、教育培训 |
| **解决的问题** | 降低协作门槛 | 防止信息泄露 | 按需授权、最小权限 |
