# 华为云 DCS (Redis) 服务客户常见问题与故障场景深度分析

> 基于 [华为云 DCS 官方文档](https://support.huaweicloud.com/dcs/index.html) 深度分析华为云分布式缓存服务（DCS for Redis）在客户实际使用中高频出现的资源扩容、性能瓶颈、稳定性风险和连接故障场景，提供根因分析与解决方案。

---

## 一、服务概览

华为云 DCS（Distributed Cache Service）是基于开源 Redis 的高性能、可扩展的分布式缓存服务，支持单机、主备、Proxy 集群和 Cluster 集群四种实例类型。

| 维度 | 说明 |
|------|------|
| 支持版本 | Redis 4.0 / 5.0 / 6.0 / 7.0 |
| 实例类型 | 单机、主备、Proxy 集群、Cluster 集群 |
| 最大内存 | 单实例最大 512GB（Cluster 可扩展至 TB 级） |
| 部署模式 | 单 AZ / 多 AZ（跨可用区容灾） |
| 访问方式 | VPC 内网访问、公网访问（NAT）、SSL/TLS 加密 |

## 三、资源扩容类问题

### 3.1 内存使用率 >95% 触发限流

**现象描述**：
- 监控面板显示内存使用率持续超过 95%
- 客户端收到 `OOM command not allowed when used memory > 'maxmemory'` 错误
- 部分写操作被拒绝，业务写入失败

**根因分析**：
- **数据量增长超出预估**：业务快速增长导致缓存数据量超出实例规格
- **过期策略配置不当**：未合理设置 Key 的 TTL，导致大量永不过期的 Key 占用内存
- **淘汰策略不适合业务**：默认 `noeviction` 策略在内存满时直接拒绝写入
- **内存碎片化**：实际数据量小于已用内存，但碎片率高导致可用内存不足

**华为云 DCS 提供的解决方案**：
1. **垂直扩容（规格变更）**：在线升级实例规格，增大内存容量（支持不中断业务的平滑扩容）
2. **水平扩容（分片扩展）**：Cluster 集群实例可增加分片数，横向扩展内存
3. **调整淘汰策略**：
   - `allkeys-lru`：优先淘汰最近最少使用的 Key（推荐通用场景）
   - `volatile-lru`：优先淘汰设置了过期时间且最近最少使用的 Key
   - `allkeys-random`：随机淘汰（适合缓存场景）
4. **设置合理的 TTL**：对非持久化数据设置过期时间
5. **清理无用 Key**：通过 SCAN 命令扫描并删除无用数据

**监控指标**：
| 指标 | 告警阈值 | 严重阈值 |
|------|---------|---------|
| 内存使用率 | >80% | >95% |
| Key 总数 | 接近预估上限 | 超出预估上限 |
| 驱逐 Key 数/分钟 | >0 | >100 |

**最佳实践**：
```
┌────────────────────────────────────────────────────┐
│          内存管理决策树                               │
│                                                      │
│  内存使用率 >80%？                                    │
│    ├─ 是 → 分析 Key 分布                              │
│    │    ├─ 有大量无 TTL 的 Key → 设置 TTL 或删除       │
│    │    ├─ 碎片率 >1.5 → 执行碎片整理（activedefrag）   │
│    │    └─ 确实需要更多内存 → 规格变更扩容              │
│    └─ 否 → 继续监控                                   │
│                                                      │
│  内存使用率 >95%？                                    │
│    ├─ 是 → 紧急处理                                   │
│    │    ├─ 调整淘汰策略（避免 noeviction）              │
│    │    ├─ 手动清理非关键数据                           │
│    │    └─ 立即发起规格变更                             │
│    └─ 否 → 设置告警并持续关注                          │
└────────────────────────────────────────────────────┘
```

### 3.2 带宽超限导致请求排队

**现象描述**：
- 客户端响应延迟突然增大
- 监控显示网络出/入带宽达到实例带宽上限
- 大 Value 读写操作（如 `GET` 一个数 MB 的 Value）尤其明显

**根因分析**：
- **大 Value 频繁读写**：单个 Value 过大（如 >10KB），占用大量带宽
- **批量操作过多**：`MGET`、`MSET` 一次操作大量 Key
- **业务高峰流量突发**：QPS 突增导致带宽打满
- **实例规格带宽不足**：低规格实例带宽上限较低

**带宽规格参考**：
| 实例规格 | 最大带宽（参考） | 建议 |
|----------|-----------------|------|
| 2GB | ~48 Mbit/s | 小规模缓存 |
| 4GB | ~96 Mbit/s | 中等规模 |
| 8GB | ~144 Mbit/s | 较大规模 |
| 32GB+ | ~576 Mbit/s+ | 大规模生产 |
| Cluster 集群 | 按分片线性叠加 | 高吞吐场景 |

**解决方案**：
1. **减小 Value 大小**：对大 Value 进行压缩（如 gzip、snappy）
2. **拆分大 Value**：将单个大 Value 拆分为多个小 Value
3. **升级实例规格**：高规格实例提供更大带宽
4. **使用 Cluster 集群**：带宽按分片数线性提升
5. **控制批量操作数量**：`MGET`/`MSET` 单次不超过 100 个 Key

### 3.3 连接数达到上限被拒绝

**现象描述**：
- 客户端报错 `max number of clients reached`
- 新连接无法建立，业务请求失败
- 监控显示连接数接近或达到上限

**根因分析**：
- **连接池配置不合理**：客户端连接池 max-total 设置过大
- **连接泄漏**：应用未正确释放连接（如异常路径未 close）
- **短连接风暴**：大量短连接频繁创建销毁，耗尽可用连接数
- **客户端数量过多**：微服务架构下过多服务实例共享同一 Redis

**连接数上限参考**：
| 实例类型 | 最大连接数（参考） |
|----------|-------------------|
| 单机/主备 | 10,000 - 80,000（按规格） |
| Proxy 集群 | 40,000 - 100,000+ |
| Cluster 集群 | 按分片叠加 |

**解决方案**：
1. **使用连接池**：合理配置连接池参数（max-total、max-idle、min-idle）
2. **排查连接泄漏**：确保 `finally` 块中释放连接
3. **使用长连接**：避免频繁创建短连接
4. **升级实例规格**：高规格实例支持更多连接
5. **监控告警**：连接数 >80% 时触发告警

**推荐连接池配置**：
```properties
# Jedis 连接池推荐配置
maxTotal=200          # 最大连接数（建议不超过实例上限/客户端数）
maxIdle=50            # 最大空闲连接
minIdle=10            # 最小空闲连接
maxWaitMillis=3000    # 获取连接最大等待时间
testOnBorrow=true     # 借出时检测连接有效性
```

### 3.4 扩容/缩容期间业务中断

**现象描述**：
- 变更规格期间出现短暂的连接中断
- 部分请求超时或返回错误
- Cluster 集群扩容时 Slot 迁移导致部分 Key 访问异常

**根因分析**：
- **主备实例规格变更**：变更过程中涉及数据迁移和主备切换，会有秒级中断
- **Cluster 扩容**：新增分片后需要迁移 Slot，迁移期间部分 Key 的访问会被重定向（`MOVED`/`ASK`）
- **Proxy 集群变更**：Proxy 节点重载期间可能有短暂抖动

**变更影响矩阵**：
| 变更类型 | 业务影响 | 中断时长 |
|----------|---------|---------|
| 单机实例规格变更 | 有中断 | 分钟级 |
| 主备实例规格变更 | 有短暂中断 | 秒 ~ 分钟级 |
| Proxy 集群规格变更 | 有短暂中断 | 秒级 |
| Cluster 集群扩分片 | 有抖动 | Slot 迁移期间 |
| 可用区变更 | 有中断 | 分钟级 |

**最佳实践**：
1. **选择低峰期操作**：在业务低峰期执行变更
2. **客户端支持重试**：配置 `MOVED`/`ASK` 重定向重试
3. **预热新分片**：Cluster 扩容后预热新分片数据
4. **分批变更**：大批量变更拆分为多次小变更

## 四、性能类问题

### 4.1 CPU 使用率飙升导致响应变慢

**现象描述**：
- 监控显示 CPU 使用率持续 >80%
- 客户端 RT（响应时间）明显增大
- 排查发现 QPS 并不高，但 CPU 依然高

**根因分析**：
- **复杂命令过度使用**：`SORT`、`SINTER`、`SUNION`、`LRANGE 0 -1` 等复杂度高的命令占用大量 CPU
- **大量 Key 过期集中淘汰**：同一时间大量 Key 过期触发批量淘汰
- **Big Key 操作**：对大 Key 执行复杂操作（如 `HGETALL` 一个 100 万字段的 Hash）
- **持久化开销**：AOF 重写（rewrite）或 RDB 生成（bgsave）期间 fork 子进程消耗 CPU
- **频繁的 `KEYS`/`SCAN`**：全量扫描操作消耗大量 CPU

**CPU 使用率诊断流程**：
```
CPU 使用率高
  │
  ├─ QPS 也高？ → 正常高负载，考虑扩容或读写分离
  │
  ├─ QPS 不高但 CPU 高？
  │    ├─ 检查慢查询 → 复杂命令/Big Key 操作？
  │    │    ├─ 是 → 优化命令使用，拆分大 Key
  │    │    └─ 否 → 继续排查
  │    │
  │    ├─ 检查是否在做持久化？
  │    │    ├─ AOF 重写 → 调整 AOF 重写触发策略
  │    │    └─ RDB 备份 → 调整备份时间窗口
  │    │
  │    ├─ 检查是否有大量 Key 同时过期？
  │    │    └─ 是 → 给 TTL 加随机偏移，避免集中过期
  │    │
  │    └─ 检查是否在执行 SCAN/KEYS？
  │         └─ 是 → 避免在线上执行全量扫描
  │
  └─ 其他 → 联系华为云技术支持
```

**解决方案**：
1. **禁用高风险命令**：通过 DCS 控制台禁用 `KEYS`、`FLUSHALL`、`FLUSHDB` 等
2. **优化复杂命令**：用 `SCAN` 替代 `KEYS`，避免对大集合执行全量操作
3. **Big Key 拆分**：将大 Key 拆分为多个小 Key
4. **TTL 随机化**：给过期时间加上随机偏移量，避免同时过期
5. **调整持久化策略**：高峰期减少 AOF fsync 频率

### 4.2 慢查询阻塞单线程事件循环

**现象描述**：
- Redis 响应延迟出现周期性毛刺
- 单线程模型下，一个慢查询阻塞后续所有请求
- 监控显示 P99 延迟远高于 P50

**根因分析**：
Redis 的核心处理逻辑是单线程的（Redis 6.0+ 仅网络 IO 多线程），一个慢命令会阻塞整个事件循环。

**常见慢查询命令及复杂度**：
| 命令 | 时间复杂度 | 危险场景 |
|------|-----------|---------|
| `KEYS *` | O(N) | 全库扫描 |
| `HGETALL` | O(N) | 大 Hash（>1万字段） |
| `SMEMBERS` | O(N) | 大 Set（>1万元素） |
| `LRANGE 0 -1` | O(N) | 大 List |
| `SORT` | O(N+M*log(M)) | 大集合排序 |
| `SINTER`/`SUNION` | O(N*M) | 多个大集合运算 |
| `DEL` | O(N) | 删除大 Key |
| `FLUSHALL`/`FLUSHDB` | O(N) | 清空数据库 |

**慢查询阈值配置**：
```properties
# 华为云 DCS 支持配置慢查询阈值（默认 10ms）
slowlog-log-slower-than 10000   # 单位：微秒
```

**解决方案**：
1. **设置慢查询日志**：通过 DCS 控制台或参数配置开启慢查询日志
2. **定期分析慢查询**：使用 `SLOWLOG GET` 查看慢查询记录
3. **替代高风险命令**：
   - `KEYS pattern` → `SCAN cursor MATCH pattern`
   - `HGETALL big_hash` → `HSCAN cursor`
   - `SMEMBERS big_set` → `SSCAN cursor`
4. **Big Key 异步删除**：Redis 4.0+ 支持 `UNLINK` 异步删除大 Key

### 4.3 Big Key（大键）导致阻塞与内存不均

**现象描述**：
- Cluster 集群中某个分片内存使用率远高于其他分片
- 删除大 Key 时出现长时间阻塞
- 网络带宽被大 Key 的读写占满

**什么是 Big Key**：
| 类型 | Big Key 判定标准（参考） |
|------|------------------------|
| String | Value > 10KB |
| Hash | 字段数 > 5,000 |
| List | 元素数 > 5,000 |
| Set | 元素数 > 5,000 |
| ZSet | 元素数 > 5,000 |

**影响分析**：
```
Big Key 影响
  │
  ├─ 内存层面
  │    ├─ 单个 Key 占用大量内存
  │    ├─ Cluster 模式下导致分片内存不均
  │    └─ 内存碎片率升高
  │
  ├─ 性能层面
  │    ├─ 读写大 Key 阻塞单线程
  │    ├─ 删除大 Key（DEL）长时间阻塞
  │    ├─ 占用大量网络带宽
  │    └─ 序列化/反序列化开销大
  │
  └─ 稳定性层面
       ├─ 主备同步延迟增大
       ├─ AOF 重写时 fork 耗时增加
       └─ 可能触发客户端超时
```

**发现 Big Key 的方法**：
1. **DCS 控制台**：华为云 DCS 提供大 Key 分析工具
2. **redis-cli**：`redis-cli --bigkeys` 扫描各类型的最大 Key
3. **`MEMORY USAGE` 命令**（Redis 4.0+）：查看单个 Key 的内存占用
4. **`SCAN` + `STRLEN`/`HLEN`/`LLEN`/`SCARD`/`ZCARD`**：遍历检查

**解决方案**：
1. **拆分大 Key**：
   - 大 Hash → 按 field 哈希拆分为多个小 Hash
   - 大 List → 按范围拆分为多个小 List
   - 大 Set → 按元素哈希拆分为多个小 Set
2. **压缩 Value**：String 类型大 Value 使用压缩算法
3. **异步删除**：使用 `UNLINK` 代替 `DEL`
4. **定期清理**：对不再使用的大 Key 设置过期时间

### 4.4 Hot Key（热键）导致访问倾斜

**现象描述**：
- Cluster 集群中某个分片 QPS 远高于其他分片
- 单个分片 CPU/带宽接近饱和
- 其他分片资源利用率低

**根因分析**：
- 少量 Key 被高频访问（如热门商品信息、排行榜 Top N）
- 分流不均，大量请求集中在少数 Key

**发现 Hot Key 的方法**：
1. **DCS 控制台**：华为云 DCS 提供 Hot Key 分析工具
2. **`MONITOR` 命令**：实时查看命令流（注意性能影响）
3. **`redis-cli --hotkeys`**（Redis 4.0+，需开启 maxmemory-policy 为 LFU）
4. **业务层统计**：在应用层对 Key 访问频率做统计

**解决方案**：
1. **本地缓存 + Redis 二级缓存**：对热数据在应用本地做一级缓存（如 Guava Cache / Caffeine），减少 Redis 访问
2. **Key 分片打散**：将一个热 Key 复制为 N 份（如 `hot_key_1` ~ `hot_key_N`），读取时随机选一个
3. **读写分离**：利用 DCS 的读写分离能力，将读请求分摊到从节点
4. **使用 Proxy 集群**：Proxy 集群可以在代理层做请求分发，缓解热点问题

**热 Key 打散示例**：
```python
import hashlib

def get_hot_key_shard(key, shard_count=10):
    """将热 Key 打散到多个 Key"""
    return f"{key}_shard_{hash(key) % shard_count}"

# 读取时随机选择一个分片
def read_hot_key(key, shard_count=10):
    import random
    shard = random.randint(0, shard_count - 1)
    return redis.get(f"{key}_shard_{shard}")

# 写入时更新所有分片
def write_hot_key(key, value, shard_count=10):
    pipe = redis.pipeline()
    for i in range(shard_count):
        pipe.set(f"{key}_shard_{i}", value)
    pipe.execute()
```

## 五、稳定性类问题

### 5.1 主备切换导致短暂不可用

**现象描述**：
- 监控显示实例状态变为"主备切换中"
- 切换期间（通常 5-30 秒）客户端连接中断
- 切换完成后客户端自动恢复（或需要重连）

**触发主备切换的场景**：
| 触发场景 | 说明 |
|----------|------|
| 主节点故障 | 主节点宕机、进程崩溃 |
| 主节点网络异常 | 主节点与哨兵/从节点网络中断 |
| 主节点资源超限 | CPU/内存持续 100% 触发保护 |
| 可用区故障 | 跨 AZ 部署时某个 AZ 不可用 |
| 运维操作 | 手动切换、规格变更、版本升级 |
| 主节点 Full GC | JVM（如果是 Proxy 集群）或 fork 操作导致长时间停顿 |

**影响分析**：
```
主备切换时间线
  │
  ├─ T+0s    哨兵检测到主节点异常
  ├─ T+5s    哨兵主观下线（SDOWN）
  ├─ T+10s   哨兵客观下线（ODOWN，多数哨兵确认）
  ├─ T+12s   哨兵发起故障转移投票
  ├─ T+15s   选出新的主节点
  ├─ T+20s   从节点升主完成，开始接受写入
  ├─ T+25s   其他从节点开始同步新主
  ├─ T+30s   客户端连接恢复
  │
  └─ 总中断时长：约 15-30 秒
```

**解决方案**：
1. **客户端重试机制**：配置合理的重试策略（指数退避）
2. **跨 AZ 部署**：使用多 AZ 实例提高可用性
3. **客户端读写分离**：读请求可以切换到从节点
4. **合理设置超时**：客户端连接超时建议 >30 秒
5. **监控告警**：配置主备切换告警，及时发现并处理

**推荐客户端重试配置**：
```java
// Lettuce 客户端重试配置
ClientOptions clientOptions = ClientOptions.builder()
    .autoReconnect(true)                    // 自动重连
    .disconnectedBehavior(DisconnectedBehavior.REJECT_COMMANDS) // 断连时拒绝命令
    .socketOptions(SocketOptions.builder()
        .connectTimeout(Duration.ofSeconds(5))   // 连接超时 5s
        .keepAlive(true)                          // 开启 TCP KeepAlive
        .build())
    .build();
```

### 5.2 AOF 持久化影响性能

**现象描述**：
- 开启 AOF 持久化后，写入延迟明显增大
- AOF 重写（rewrite）期间 CPU/内存波动
- 高写入场景下性能下降 20%-40%

**AOF 策略对比**：
| 策略 | 每秒 fsync 频率 | 数据安全性 | 性能影响 |
|------|-----------------|-----------|---------|
| `always` | 每次写入都 fsync | 最高（最多丢 1 条） | **严重**（性能下降 40%+） |
| `everysec` | 每秒 fsync 一次 | 较高（最多丢 1 秒数据） | **中等**（推荐） |
| `no` | 由 OS 决定 | 低（可能丢数秒数据） | 最小 |

**根因分析**：
- **fsync 阻塞**：`always` 模式下每次写入都要等待磁盘 fsync 完成
- **AOF 重写**：fork 子进程进行 AOF 重写时，主进程的写操作需要维护"重写缓冲区"
- **磁盘 I/O 竞争**：AOF 文件写入与业务请求争抢磁盘 I/O

**AOF 重写影响流程**：
```
┌─────────────────────────────────────────────────────┐
│              AOF 重写过程                              │
│                                                       │
│  1. 主进程 fork 子进程                                │
│     ├─ fork 期间主进程阻塞（数据量越大，阻塞越久）       │
│     └─ 内存使用量翻倍（Copy-On-Write）                │
│                                                       │
│  2. 子进程重写 AOF                                    │
│     ├─ 扫描所有 Key，生成最简写入命令                   │
│     └─ 写入临时 AOF 文件                              │
│                                                       │
│  3. 主进程继续处理请求                                 │
│     ├─ 新的写入命令同时写入旧 AOF + 重写缓冲区          │
│     └─ 重写缓冲区持续增长                              │
│                                                       │
│  4. 子进程完成重写                                     │
│     ├─ 将重写缓冲区追加到新 AOF                        │
│     ├─ 替换旧 AOF 文件                                │
│     └─ 期间有短暂阻塞（信号量等待）                     │
└─────────────────────────────────────────────────────┘
```

**解决方案**：
1. **使用 `everysec` 策略**（推荐）：在数据安全性和性能之间取得平衡
2. **调整 AOF 重写触发条件**：
   ```properties
   auto-aof-rewrite-percentage 100   # AOF 文件增长 100% 时触发重写
   auto-aof-rewrite-min-size 64mb    # AOF 文件最小 64MB 才触发重写
   ```
3. **缓存场景不开启 AOF**：纯缓存场景建议关闭 AOF，使用 RDB 或无持久化
4. **使用高性能磁盘**：DCS 实例使用 SSD 存储

### 5.3 内存碎片率过高

**现象描述**：
- `INFO memory` 显示 `mem_fragmentation_ratio` > 1.5
- 实际数据量远小于已用内存
- 可用内存不足但数据量不大

**内存碎片率指标**：
| 碎片率 | 状态 | 建议 |
|--------|------|------|
| 1.0 - 1.5 | 正常 | 无需处理 |
| 1.5 - 2.0 | 轻微碎片化 | 关注监控 |
| 2.0 - 3.0 | 中度碎片化 | 建议开启 activedefrag |
| >3.0 | 严重碎片化 | 立即处理 |

**根因分析**：
- 频繁的增删改操作导致内存分配器（jemalloc）产生大量碎片
- Big Key 的分配和释放导致大块内存碎片
- Redis 的内存分配策略（按 2 的幂次方分配）导致对齐浪费

**解决方案**：
1. **开启主动碎片整理**（Redis 4.0+）：
   ```properties
   activedefrag yes
   active-defrag-threshold-lower 10    # 碎片率 >10% 开始整理
   active-defrag-threshold-upper 100   # 碎片率 >100% 尽力整理
   ```
2. **重启实例**：重启可以彻底消除碎片（会短暂中断）
3. **避免频繁增删**：业务设计上减少对同一 Key 的频繁增删
4. **选择合适的分配器**：jemalloc 通常比 glibc malloc 更优

---

### 5.4 内存泄漏（Key 未过期/未删除）

**现象描述**：
- 内存使用量持续增长，无法通过淘汰策略回收
- `INFO keyspace` 显示 Key 数量持续增长
- 大量 Key 没有设置 TTL 或 TTL 设置过长

**根因分析**：
- **忘记设置 TTL**：开发时遗漏了过期时间设置
- **业务逻辑缺陷**：生成 Key 的规则变化导致旧 Key 永远不会被访问也不会被清理
- **序列化格式变更**：Key 格式改变后旧格式 Key 变成"僵尸 Key"

**诊断方法**：
1. **Key 前缀统计**：
   ```bash
   # 统计各前缀的 Key 数量
   redis-cli --scan --pattern "prefix:*" | wc -l
   ```
2. **TTL 分布分析**：
   ```bash
   # 查看没有设置 TTL 的 Key
   redis-cli --scan | while read key; do
     ttl=$(redis-cli TTL "$key")
     if [ "$ttl" -eq "-1" ]; then
       echo "$key"
     fi
   done
   ```
3. **华为云 DCS 控制台**：提供 Key 分析工具，可按前缀、类型、TTL 筛选

**解决方案**：
1. **强制 TTL 规范**：所有缓存 Key 必须设置 TTL（代码 Review 强制检查）
2. **Key 命名规范**：使用 `{业务}:{实体}:{ID}` 格式，便于批量清理
3. **定期扫描清理**：定时任务扫描并清理过期/无用 Key
4. **使用 `SCAN` + `TTL` 定期审计**：每周统计各前缀的 Key 数量和 TTL 分布

## 六、连接与故障类问题

### 6.1 客户端连接超时/断连

**现象描述**：
- 客户端报错 `Connection timed out` 或 `Connection reset by peer`
- 连接池中的连接突然全部失效
- 间歇性出现连接断开

**根因分析**：
- **网络抖动**：VPC 内网络抖动导致 TCP 连接中断
- **服务端超时设置**：`timeout` 参数导致空闲连接被服务端主动断开
- **TCP KeepAlive 配置**：操作系统或 Redis 的 TCP KeepAlive 参数不匹配
- **安全组/网络 ACL 变更**：安全组规则变更导致网络不通
- **Redis 实例重启**：实例维护、升级等导致连接断开

**相关参数**：
| 参数 | 默认值 | 说明 |
|------|--------|------|
| `timeout` | 0（永不超时） | 客户端空闲 N 秒后断开，0 表示不断开 |
| `tcp-keepalive` | 300（秒） | TCP KeepAlive 探测间隔 |
| `tcp-backlog` | 511 | TCP 连接队列长度 |

**解决方案**：
1. **设置合理的 `timeout`**：建议设为 300 秒或 0
2. **开启 TCP KeepAlive**：确保操作系统和 Redis 都开启 KeepAlive
3. **客户端心跳**：连接池配置定时 ping 检测
4. **客户端重连机制**：配置自动重连和重试策略
5. **网络稳定性检查**：排查是否有网络设备故障或配置变更

**推荐连接配置**：
```properties
# 应用层连接池配置
# 连接超时
connectTimeout=3000
# 读超时
readTimeout=3000
# 重试次数
retryAttempts=3
# 重试间隔
retryInterval=1500
# 心跳检测间隔
pingConnectionInterval=30000
# 连接空闲超时
idleConnectionTimeout=60000
```

### 6.2 OOM（内存不足）导致驱逐/拒绝

**现象描述**：
- 客户端收到 `OOM command not allowed when used memory > 'maxmemory'` 错误
- 大量 Key 被驱逐（监控显示驱逐数激增）
- 业务读取到空值（缓存被驱逐）

**OOM 触发流程**：
```
┌─────────────────────────────────────────────────────────┐
│              OOM 触发与处理流程                            │
│                                                           │
│  1. 写入请求到达                                          │
│     │                                                     │
│     ▼                                                     │
│  2. 检查 used_memory > maxmemory？                        │
│     │                                                     │
│     ├─ 否 → 正常执行写入                                  │
│     │                                                     │
│     └─ 是 → 检查淘汰策略                                  │
│          │                                                │
│          ├─ noeviction → 拒绝写入，返回 OOM 错误           │
│          ├─ allkeys-lru → 淘汰最近最少使用的 Key           │
│          ├─ volatile-lru → 淘汰有 TTL 且最少使用的 Key     │
│          ├─ allkeys-lfu → 淘汰最不经常使用的 Key           │
│          ├─ volatile-lfu → 淘汰有 TTL 且最不经常使用的 Key │
│          ├─ allkeys-random → 随机淘汰                     │
│          └─ volatile-random → 随机淘汰有 TTL 的 Key        │
└─────────────────────────────────────────────────────────┘
```

**解决方案**：
1. **紧急处理**：
   - 手动删除非关键 Key 释放内存
   - 临时调大实例规格
   - 修改淘汰策略为 `allkeys-lru`
2. **长期预防**：
   - 合理设置 Key 的 TTL
   - 定期分析内存使用趋势
   - 设置内存使用率告警（80% 预警、90% 告警）
   - 选择合适的淘汰策略

**淘汰策略选型**：
| 场景 | 推荐策略 | 原因 |
|------|---------|------|
| 纯缓存 | `allkeys-lru` | 自动淘汰冷数据，无需关心数据丢失 |
| 缓存 + 部分持久数据 | `volatile-lru` | 保护无 TTL 的 Key，仅淘汰有 TTL 的 |
| 消息队列 | `noeviction` | 不允许数据丢失 |
| 热点数据缓存 | `allkeys-lfu` | 保留高频访问的热数据 |

### 6.3 跨 VPC/Region 访问异常

**现象描述**：
- 不同 VPC 的客户端无法连接 DCS 实例
- 跨 Region 访问延迟高或连接失败
- 通过公网访问不稳定

**根因分析**：
- DCS 实例默认只能在同一 VPC 内访问
- 跨 VPC 需要通过 VPC 对等连接或企业路由器（ER）
- 跨 Region 需要通过云连接（CC）或公网
- 公网访问需要通过 NAT 网关或 ELB 转发

**网络访问方案**：
| 访问方式 | 延迟 | 稳定性 | 配置复杂度 | 适用场景 |
|----------|------|--------|-----------|---------|
| 同 VPC 直连 | <1ms | 高 | 低 | 标准部署 |
| 跨 VPC（对等连接） | 1-5ms | 中 | 中 | 多 VPC 互通 |
| 跨 Region（云连接） | 10-100ms | 中 | 高 | 跨区域容灾 |
| 公网（NAT/ELB） | 不确定 | 低 | 中 | 开发测试 |
| VPN/专线 | 5-50ms | 高 | 高 | 混合云 |

**解决方案**：
1. **同 VPC 部署**：推荐将应用与 DCS 部署在同一 VPC
2. **跨 VPC 配置对等连接**：建立 VPC 对等连接并配置路由
3. **使用公网访问**：开启 DCS 的公网访问功能（仅建议开发测试环境）
4. **安全组配置**：确保安全组放行 Redis 端口（默认 6379）

## 九、故障排查速查表

| 故障现象 | 可能原因 | 排查步骤 |
|----------|---------|---------|
| 写入返回 OOM | 内存满 | 检查内存使用率 → 分析 Key 分布 → 调整淘汰策略 |
| 响应变慢 | CPU 高/慢查询/Big Key | 检查 CPU 使用率 → 查看慢查询 → 分析大 Key |
| 连接被拒绝 | 连接数满/安全组 | 检查连接数 → 检查安全组 → 检查客户端连接池 |
| 数据丢失 | 主备切换/淘汰/过期 | 检查主备切换记录 → 检查驱逐数 → 检查 TTL |
| 主备频繁切换 | 网络不稳定/资源不足 | 检查网络延迟 → 检查 CPU/内存 → 联系华为云支持 |
| 内存持续增长 | Key 泄漏/碎片 | 分析 Key TTL 分布 → 检查碎片率 → 开启 defrag |
| Cluster 分片不均 | Big Key/Hot Key | 缓存分析 → 大 Key/热 Key 拆分 |
| AOF 重写失败 | 磁盘空间不足 | 检查磁盘使用率 → 清理旧 AOF 文件 |

## 十、总结

华为云 DCS (Redis) 服务在客户使用中最常见的 15 类问题可归纳为以下核心规律：

1. **内存管理是第一要务**：内存使用率 >95% 和 OOM 是最常见的问题，合理的 TTL、淘汰策略和容量规划是预防基础
2. **Big Key / Hot Key 是性能杀手**：单个大 Key 或热 Key 可以拖垮整个分片甚至整个实例
3. **单线程模型的限制**：Redis 单线程处理命令的特性决定了任何阻塞操作都会影响全局
4. **持久化与性能的权衡**：AOF `always` 策略对性能影响巨大，大多数场景 `everysec` 足够
5. **网络与连接管理**：跨 VPC/Region 访问、连接池配置不当是连接类问题的根源
6. **监控告警是运维基石**：及时发现、及时处理，避免小问题演变为大故障
