# 华为云 ModelArts 大页内存与绑核深度分析

## 1. 概述

在 ModelArts 专属资源池中，**大页内存（Huge Pages）** 和 **绑核（CPU Affinity / NUMA 绑定）** 是两项关键的底层性能优化操作。两者协同工作，目标是解决 **Host 侧算子下发瓶颈**——即 CPU 向 NPU 下发计算任务时的延迟问题。

华为官方 MA-Advisor 性能诊断工具实测，结合绑核 + 大页等优化后，昇腾训练可提升 **10%-30%** 的性能。

---

## 2. 背景知识：昇腾训练的 Host-Device 架构

PyTorch 在昇腾 AI 处理器上的加速实现方式是**以算子为粒度进行调用（OP-based）**，即通过 Python 与 C++ 调用 CANN 层接口 AscendCL 调用一个或多个亲和算子。

在此过程中：
- **CPU（Host）**：负责算子的下发（构造计算图、准备参数、调用 AscendCL 接口）
- **NPU（Device）**：负责算子的执行

算子下发和执行**异步发生**，性能瓶颈主要体现在：

1. **理想情况**：CPU 侧算子下发明显比 NPU 侧算子执行更快，性能瓶颈集中在 NPU 侧
2. **实际问题**：CPU 侧算子下发不够快，NPU 出现空转等待（NPU 利用率下降）

大页内存和绑核的目标就是**减少 Host 算子下发时间**，使 NPU 流水线持续满载。

---

## 3. 大页内存（Huge Pages）

### 3.1 解决的核心问题

Linux 默认内存页大小为 **4KB**。AI 训练场景中，模型参数、梯度、激活值等数据量巨大（数十 GB），使用 4KB 页会导致：

- **TLB 容量不足**：TLB（Translation Lookaside Buffer）是 CPU 内部缓存虚拟地址→物理地址映射的硬件，容量有限（通常几百到几千条目）。以 70B 模型为例，仅模型参数就约 140GB，需要 140GB ÷ 4KB = **3,500 万条页表项**，远超 TLB 容量
- **TLB Miss 频繁** → 触发 Page Table Walk → 多次内存访问 → **CPU 等待时间增加**
- **Host 侧算子下发延迟**：CPU 频繁做内存地址翻译会拖慢算子下发速度，导致 NPU 空转

### 3.2 大页内存的效果

| 页大小 | 140GB 模型所需页表项 | TLB 命中率变化 |
|--------|---------------------|---------------|
| 4KB（默认） | 3,500 万 | 极低（频繁 Miss） |
| 2MB（大页） | 6.7 万 | 大幅提升 |
| 1GB（大页） | 140 | 接近 100% |

**核心效果**：减少 TLB Miss，加速 CPU 侧内存访问，缩短 Host 算子下发时间 → NPU 流水线不空转。

### 3.3 TLB Miss 对性能的影响原理

```
正常情况（TLB Hit）：
  CPU 需要访问内存地址 0x7fff80000000
    → TLB 查找 → 命中 → 物理地址直接获取
    → 1 个时钟周期

TLB Miss 情况：
  CPU 需要访问内存地址 0x7fff80000000
    → TLB 查找 → 未命中
    → Page Table Walk（多级页表遍历，4-5 次内存访问）
    → 每次内存访问约 100-300 个时钟周期
    → 总延迟：400-1500 个时钟周期

大页内存（2MB 页）：
  同样 140GB 内存
    → TLB 只需覆盖 6.7 万条目
    → 命中率接近 100%
    → 几乎消除 Page Table Walk 开销
```

### 3.4 适用场景

| 场景 | 是否需要 | 原因 |
|------|----------|------|
| **大模型训练（≥7B）** | 强烈推荐 | 参数量大，内存访问密集 |
| **多机多卡分布式训练** | 强烈推荐 | HCCL 通信缓冲区需要大块连续内存 |
| **昇腾 NPU 训练** | 推荐 | NPU 通过 DMA 搬运数据，大页减少内存碎片，提升 DMA 效率 |
| **小模型推理** | 一般 | 内存压力较小，收益有限 |
| **数据预处理为主** | 不需要 | 瓶颈在 IO，不在内存访问 |

### 3.5 潜在业务提升

| 指标 | 提升幅度 | 说明 |
|------|----------|------|
| 训练吞吐量 | +5%-15% | 减少 Host 侧算子下发延迟，NPU 利用率提高 |
| HCCL 集合通信效率 | 显著提升 | 大块连续内存减少 DMA 搬运次数，AllReduce/AllGather 延迟降低 |
| 内存碎片 | 大幅减少 | 大页内存预分配，避免运行时内存碎片化导致的 OOM |
| 时延稳定性 | P99 更稳定 | 减少 Page Fault 引起的尾延迟抖动 |

## 4. 绑核（CPU Affinity / NUMA 绑定）

### 4.1 解决的核心问题

昇腾训练服务器通常是**多路 NUMA 架构**（如双路/四路 CPU），每个 CPU 插槽有自己的本地内存，访问远端内存的延迟是本地的 **1.5-2 倍**。

```
┌──────────────────────────────────────────────────┐
│              昇腾训练服务器（双路示例）              │
│                                                    │
│  ┌─────────────┐              ┌─────────────┐    │
│  │  NUMA Node 0 │              │  NUMA Node 1 │    │
│  │  CPU 0-23    │  QPI/UPI    │  CPU 24-47   │    │
│  │  内存 128GB  │◄───────────►│  内存 128GB  │    │
│  │              │  跨NUMA延迟  │              │    │
│  │  NPU 0-3     │  增加50-100% │  NPU 4-7     │    │
│  │  (PCIe直连)  │              │  (PCIe直连)  │    │
│  └─────────────┘              └─────────────┘    │
└──────────────────────────────────────────────────┘
```

### 4.2 不绑核时的四个核心问题

| 问题 | 影响 | 严重程度 |
|------|------|----------|
| **跨 NUMA 访问** | NPU 0 的训练进程被调度到 NUMA Node 1 的 CPU 上，每次算子下发需跨 NUMA 读写内存，延迟增加 50-100% | 严重 |
| **CPU 缓存失效** | 进程在不同 CPU 核心间迁移，L1/L2 缓存全部失效 | 中等 |
| **上下文切换开销** | OS 调度器可能将进程迁移到其他核心 | 中等 |
| **HCCL 通信低效** | NPU 间的集合通信需要 CPU 参与，跨 NUMA 的 CPU 协调增加延迟 | 严重 |

### 4.3 绑核后的数据路径

```
NPU 0 的训练进程 → 绑定到 NUMA Node 0 的 CPU 0-5
  → 内存分配在 NUMA Node 0（本地内存）
  → NPU 0 通过 PCIe 直连 NUMA Node 0
  → CPU 算子下发 → 本地内存 → DMA → NPU 0
  → 全程不跨 NUMA，延迟最优
```

### 4.4 NUMA 架构的延迟对比

| 操作 | 本地 NUMA | 跨 NUMA | 差异 |
|------|-----------|---------|------|
| 内存读取延迟 | ~80ns | ~140ns | +75% |
| 内存带宽 | ~80 GB/s | ~40 GB/s | -50% |
| L3 缓存命中率 | ~95% | ~60%（迁移后） | -35% |
| PCIe 设备通信 | 直连 | 需跨 QPI/UPI | +50-100% |

### 4.5 适用场景

| 场景 | 是否需要 | 原因 |
|------|----------|------|
| **单机多卡训练** | 强烈推荐 | 避免跨 NUMA 调度，每卡绑定对应 NUMA 的 CPU |
| **多机多卡分布式** | 强烈推荐 | HCCL 通信需要 CPU 协调，绑核减少通信延迟 |
| **昇腾 NPU 训练（全部）** | 推荐 | NPU 与 CPU 的 NUMA 亲和性直接影响 Host-Device 数据搬运效率 |
| **推理服务** | 推荐 | 降低尾延迟抖动 |
| **CPU 密集型任务** | 视情况 | 如果是纯 CPU 计算，绑核防迁移即可 |

### 4.6 潜在业务提升

| 指标 | 提升幅度 | 说明 |
|------|----------|------|
| 单卡训练吞吐量 | +10%-30% | 减少跨 NUMA 延迟 + 减少缓存失效 |
| 分布式训练线性度 | 显著提升 | HCCL 通信延迟降低，多卡加速比更接近线性 |
| 尾延迟 | P99 更稳定 | OS 调度抖动减少 |
| NPU 利用率 | 从 60-70% 提升到 85-95% | Host 侧算子下发更快，NPU 空转时间减少 |

## 5. 两者协同的叠加效应

大页内存和绑核**不是独立的优化，而是协同工作的**：

```
                  优化前                          优化后
              ┌───────────┐                  ┌───────────┐
              │ CPU 调度到 │                  │ CPU 绑定到 │
              │ 随机核心   │                  │ NUMA Node 0│
              │           │                  │           │
              │ 4KB 页    │                  │ 2MB/1GB   │
              │ TLB Miss  │                  │ TLB Hit   │
              │ 频繁      │                  │ 率高      │
              │           │                  │           │
              │ 跨 NUMA   │                  │ 本地内存  │
              │ 访问 NPU  │                  │ 直连 NPU  │
              └─────┬─────┘                  └─────┬─────┘
                    │                              │
                    ▼                              ▼
              NPU 空转等待                    NPU 流水线
              算子下发慢                      持续满载
              利用率 60-70%                   利用率 85-95%
```

### 5.1 叠加效果对比

| 优化组合 | 典型提升 | NPU 利用率 |
|----------|----------|-----------|
| 无优化 | 基线 | 60-70% |
| 仅大页 | +5-10% | 65-75% |
| 仅绑核 | +10-20% | 75-85% |
| **大页 + 绑核** | **+15-30%** | **85-95%** |

### 5.2 为什么是协同而非独立

1. **绑核确保 NUMA 本地性** → 内存访问集中在同一个 NUMA 节点
2. **大页减少页表开销** → 本地 NUMA 节点上的内存访问更快
3. 两者结合 → **CPU 算子下发的总延迟 = NUMA 本地延迟 × (1 - TLB 命中率提升)** → 乘法效应

## 7. ModelArts 中的配置方式

### 7.1 大页内存配置

```bash
# 方式1：系统级大页配置（需提工单由华为工程师配置）
# /etc/default/grub 中添加
default_hugepagesz=1G hugepagesz=1G hugepages=<页数>

# 方式2：训练作业启动脚本中
# 确认透明大页（THP）状态
cat /sys/kernel/mm/transparent_hugepage/enabled
# 如果是 madvise，可以设置为 always
echo always > /sys/kernel/mm/transparent_hugepage/enabled

# 方式3：HCCL 通信缓冲区（利用大页）
export HCCL_BUFFSIZE=120  # 单位 MB，默认较小，增大可利用大页内存
```

### 7.2 绑核配置

```bash
# 方式1：训练作业启动命令中使用 numactl
# 单卡训练，绑定到 NPU 对应的 NUMA 节点
numactl --cpunodebind=0 --membind=0 python train.py --device 0

# 多卡训练，每个进程绑定对应 NUMA
for i in 0 1 2 3; do
    numactl --cpunodebind=$((i/4)) --membind=$((i/4)) \
        python train.py --device $i &
done

# 方式2：使用 taskset 绑定具体 CPU 核心
taskset -c 0-5 python train.py --device 0
taskset -c 6-11 python train.py --device 1

# 方式3：在 MindSpore 中自动 NUMA 感知
# MindSpore 框架在 Ascend 后端会自动做一定的 NUMA 亲和调度
import mindspore as ms
ms.set_context(device_target="Ascend")
```

### 7.3 NPU 与 NUMA 节点映射查询

```bash
# 查询 NPU 设备的 NUMA 亲和性
npu-smi info                    # 查看 NPU 设备列表
lspci -vvv -s <pci_address>    # 查看 NPU 的 PCIe 地址和 NUMA 节点
cat /sys/bus/pci/devices/<pci_address>/numa_node  # 直接查看 NUMA 节点号

# 查看 CPU 与 NUMA 的映射
numactl --hardware              # 查看 NUMA 拓扑
lscpu | grep "NUMA node"        # 查看 CPU 到 NUMA 的映射
```

## 8. 注意事项与限制

| 注意点 | 说明 |
|--------|------|
| **大页内存预分配** | 系统启动时预分配，不可动态调整，需预留足够的大页 |
| **绑核需要规划** | 多卡训练时需正确映射 NPU → NUMA → CPU，错误映射反而降低性能 |
| **容器环境限制** | ModelArts 容器中部分系统级配置需提工单由华为工程师操作 |
| **与弹性资源冲突** | 开启绑核后，逻辑子池的弹性扩缩可能受 NUMA 限制 |
| **不是万能优化** | 如果瓶颈在 NPU 计算本身（非 Host 下发），大页和绑核的收益有限 |
| **需先 Profiling** | 建议先用 MA-Advisor 工具采集 Profiling 数据，确认瓶颈在 Host 侧再做优化 |

## 9. 性能调优建议流程

```
1. 采集 Profiling 数据
   使用 ModelArts MA-Advisor 工具采集训练 Profiling 数据

2. 分析瓶颈位置
   ├── NPU 利用率 > 85% → 瓶颈在 NPU 侧 → 优化算子/模型结构
   └── NPU 利用率 < 85% → 瓶颈在 Host 侧 → 继续以下步骤

3. 开启大页内存
   → 测量 NPU 利用率变化

4. 开启绑核（NUMA 亲和）
   → 测量 NPU 利用率变化

5. 调整 HCCL 参数
   export HCCL_BUFFSIZE=120
   export HCCL_CONNECT_TIMEOUT=7200

6. 验证整体提升
   对比优化前后的训练吞吐量（tokens/s 或 samples/s）
```

## 10. 总结

| 对比项 | 大页内存（Huge Pages） | 绑核（CPU Affinity） |
|--------|----------------------|---------------------|
| **解决的问题** | TLB Miss 频繁导致内存访问慢 | 跨 NUMA 访问延迟 + CPU 缓存失效 |
| **优化层面** | 内存管理 | CPU 调度 |
| **典型提升** | +5-15% | +10-30% |
| **协同效果** | **两者叠加可达 +15-30%** | |
| **适用场景** | 大模型训练、分布式训练 | 所有昇腾 NPU 训练 |
| **风险** | 预分配内存不可动态调整 | 错误映射反而降低性能 |
| **配置方式** | 系统级/环境变量 | numactl/taskset/启动脚本 |
