## 1. 架构概述

### 1.1 系统组件

| 组件 | 角色 | 部署位置 | 数量 |
|------|------|----------|------|
| **vLLM Prefill 实例 (P)** | KV Cache 生产者 | 昇腾服务器 (K8s Pod) | **8 台** |
| **vLLM Decode 实例 (D)** | KV Cache 消费者 | 昇腾服务器 (K8s Pod) | **8 台** |
| **Mooncake Transfer Engine** | RDMA/TCP 零拷贝传输 | 每台昇腾服务器 | 16 份 |
| **Mooncake Bootstrap Server** | P2P 服务发现 | 每个 P 实例 Rank 0 | 8 个 |
| **Mooncake Master Server** | 分布式存储协调器 (Store 模式) | K8s Pod | **1 主 + 2 从** |
| **Proxy 代理** | 请求路由与分发 | K8s Pod 或独立 | 至少 1 个 |
| **etcd** | 元数据存储后端 | K8s Pod | **1 主 + 2 从** |

### 1.3 请求流转路径

```
Client → Proxy (Round-Robin 选择 P 和 D)
       → Prefill-P[i] (计算 KV Cache, do_remote_decode=True, max_tokens=1)
       → KV Cache 通过 Mooncake RDMA 传输到 Decode-D[j]
       → Decode-D[j] (加载 KV Cache, 生成剩余 tokens)
       → Proxy → Client (流式响应)
```

### 1.4 关键架构特征

#### 跨副本 KV Cache 共享

MooncakeStoreConnector 的 `PoolKey` 结构**不包含 `dp_rank`**，key 由 `{model_name}@tp_rank:{tp}@pp_rank:{pp}@group:{group}@{chunk_hash}` 构成。这意味着：

- ✅ **D-3 可以加载 P-5 产生的 KV Cache** — 跨副本共享是设计意图
- ✅ 前缀缓存天然去重 — 多个 P 实例存储相同前缀时自动 dedup
- ⚠️ Store 不可用时影响**所有 8 个副本**的跨副本 Cache 命中

#### P2P 模式 vs Store 模式

| 特性 | P2P (MooncakeConnector) | Store (MooncakeStoreConnector) |
|------|------------------------|-------------------------------|
| KV 传输范围 | **配对 P-D 之间** | **全局共享** |
| 跨副本共享 | ❌ D 只能从指定的 P 加载 | ✅ 任意 D 可加载任意 P 的 KV |
| 故障爆炸半径 | 单副本对 | 整个 Store 不可用影响全部副本 |
| 依赖组件 | Bootstrap Server | Master Server + etcd |

### 1.5 关键部署参数

| 参数 | 值 | 风险说明 |
|------|-----|----------|
| Prefill 副本数 | **8** | 单 P 故障损失 12.5% 容量 |
| Decode 副本数 | **8** | 单 D 故障损失 12.5% 容量 |
| Mooncake Master 副本数 | 3 (1 Primary + 2 Follower) | K8s 层面有 HA |
| etcd 副本数 | 3 (1 Primary + 2 Follower) | K8s 层面有 HA，仲裁需 2/3 |
| Mooncake ↔ etcd 反亲和 | **未配置** | Pod 可能共处同一 Node |
| vLLM 侧 `master_server_address` | **单一字符串** | 仅指向一个端点，无 Failover |
| vLLM 侧重试/重连 | **无** | 操作失败直接记录日志 |
| Proxy 调度策略 | **Round-Robin** | 无负载感知，无健康检查（mooncake_connector_proxy.py） |
| Proxy 失败实例移除 | **仅 disagg_proxy_demo.py 支持** | mooncake_connector_proxy.py 不支持 |

### 1.6 核心矛盾

> **推理面有 8 副本冗余，但控制面（Mooncake Master + etcd）和路由面（Proxy）仍然是单点。** 控制面故障会同时影响全部 8 个副本，路由面故障会让整个系统对外不可用。

## 3. K8s 无反亲和级联故障

> Mooncake Master 和 etcd 均 1 主 2 从部署在 K8s 上，无 Pod 反亲和规则。
> **共处概率**：至少一个 Node 同时运行 Mooncake + etcd Pod ≈ **77.8%**。

### 3.1 [K1] 单 Node 宕机 → Mooncake + etcd 双 Leader 同时丢失

| 维度 | 描述 |
|------|------|
| **故障描述** | Mooncake Leader 和 etcd Leader 的 Pod 共处同一 Node，该 Node 宕机导致双 Leader 同时丢失 |
| **发生概率** | 🟠 中偏高 (~33% 概率双 Leader 共处) |
| **影响程度** | 🔴🔴 **极严重** — 全部 8 副本的 Store 操作受影响 |
| **影响范围** | **8P + 8D = 16 个实例的 KV Cache 存取** |

**级联路径**：

```
K8s Node A 宕机
  │
  ├─→ Mooncake Master Leader Pod 挂了
  │     ├─ 剩余 2 Follower 争抢 Leader
  │     ├─ 选举期间所有写操作阻塞
  │     └─ ⚠️ 16 个 vLLM Worker 不会自动重连新 Leader
  │
  └─→ etcd Leader Pod 也挂了（同 Node）
        ├─ 剩余 2 成员争抢（需 2/3 仲裁）
        ├─ 选举期间所有读写阻塞 1-5 秒
        ├─→ Mooncake 新 Leader 需读 etcd → etcd 还在选举 → 等待
        └─→ 双重选举叠加: 10-30 秒恢复（正常 2-5 秒）
              │
              └─→ 在此窗口内：
                    ├─ 8 个 P 实例的 batch_put 全部失败 → KV 无法保存
                    ├─ 8 个 D 实例的 batch_get 全部失败 → KV 无法加载
                    └─ 16 个实例的 lookup 返回 0 → 全部降级为全量计算
```

### 3.2 [K2] 网络抖动触发双组件同时选举（活锁风险）

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴 **严重** — 全部 8 副本在选举窗口内降级 |
| **量化影响** | 有反亲和：~5s 恢复，可用性损失 0.83%；无反亲和：~20s，损失 3.33% |

### 3.3 [K3] Node 资源争抢导致持续性能退化

| 维度 | 描述 |
|------|------|
| **影响程度** | 🟡 **中等** — 全部 8 副本的 Store 操作延迟持续升高 |
| **发生概率** | 🔴 极高 (~78%) |

### 3.4 [K4] 滚动更新期间服务反复中断

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴 **严重** — 每次滚动步骤可能触发双选举，总中断 30-90 秒 |
| **发生概率** | 🔴 确定（每次更新都会发生） |

### 3.5 [K5] 两 Node 宕机 → etcd 丧失仲裁 → 永久不可用

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴🔴🔴 **灾难级** — 全部 8 副本永久不可用，需手动重建 etcd |
| **恢复时间** | 30 分钟 - 数小时 |

### 3.6 [K6] vLLM Worker 连接端点不是当前 Leader

| 维度 | 描述 |
|------|------|
| **影响程度** | 🟡~🔴 **中等到严重** — 16 个 Worker 都指向固定 IP |
| **发生概率** | 🔴 极高 — 每次 Mooncake Leader 切换后必然发生 |

### 3.7 [K7] K8s OOM Kill 同时杀掉同 Node 的 Mooncake + etcd

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴 **严重** — 全部 8 副本的 Store 操作受影响 |

### 3.8 [K8] Worker 初始化时 Master 正在选举 → 启动失败

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴 **严重** — 单副本启动失败 |

## 4. Mooncake Master / etcd 故障（影响全部 8 副本）

> ⚠️ **这是当前架构最大的爆炸半径问题**：控制面只有 3 个副本，但影响全部 16 个推理实例。

### 4.1 Mooncake Master 完全不可用

| 维度 | 描述 |
|------|------|
| **故障描述** | Mooncake Master 3 个 Pod 全部不可用 |
| **影响范围** | **全部 8P + 8D 的 Store 操作失败** |
| **影响程度** | 🔴 **严重** — 跨副本 KV Cache 共享完全失效 |
| **故障表现** | 16 个 Worker 的 batch_put/batch_get 操作超时或返回错误。lookup 返回 0，全部降级为全量 Prefill |
| **级联效应** | 全量 Prefill 导致 P 端计算量飙升 → 可能引发 P 端资源耗尽 → 更多请求失败 |
| **代码位置** | `store/worker.py` (store 操作), `store/worker.py:1394` (lookup 返回 0) |

### 4.2 etcd 集群完全不可用

| 维度 | 描述 |
|------|------|
| **故障描述** | etcd 3 个节点全部不可用 |
| **影响范围** | Mooncake Master 无法读写元数据 → Store 功能完全瘫痪 |
| **影响程度** | 🔴 **严重** — 同 4.1，全部 8 副本受影响 |
| **级联路径** | etcd 不可用 → Master 无法服务 → 16 个 Worker Store 操作失败 → 全量重计算 |

### 4.3 etcd Leader 频繁切换

| 维度 | 描述 |
|------|------|
| **影响程度** | 🟡 **中等** — 全部 8 副本间歇性延迟升高 |
| **量化影响** | 每次切换 1-5 秒，频繁切换导致 Store 操作 RT 不稳定 |

### 4.4 etcd 数据损坏

| 维度 | 描述 |
|------|------|
| **影响程度** | 🔴 **严重** — 段分配信息错误，可能导致 RDMA 操作访问无效内存 |
| **影响范围** | 全部 16 个 Worker |

### 4.5 Master Server 段分配不均

| 维度 | 描述 |
|------|------|
| **影响程度** | 🟡 **中等** — 部分 P 实例存储失败，触发反压机制 |
| **代码位置** | `store/worker.py:647-701` (MOONCAKE_NO_AVAILABLE_HANDLE, backpressure) |

### 4.6 etcd 在 8 副本负载下的性能瓶颈

| 维度 | 描述 |
|------|------|
| **故障描述** | 8P8D 全负载运行时，16 个 Worker 同时访问 Store → etcd 压力激增 |
| **影响程度** | 🟡 **中等** — etcd 延迟升高传导至 Store 操作 |
| **加重因素** | 跨副本 prefix caching 导致大量 batch_is_exist 查询 → etcd 读压力 |

## 5. 单副本故障（1P 或 1D）

> 8 副本架构下，单副本故障的影响被限制在 12.5% 容量损失。相比 1P1D 架构，这是显著的改进。

### 5.1 单个 P 实例崩溃

| 维度 | 描述 |
|------|------|
| **故障描述** | 8 个 Prefill 实例中某一个崩溃 |
| **影响范围** | 该 P 实例正在处理的请求丢失，对应的 Bootstrap Server 不可用 |
| **影响程度** | 🟡 **中等** — 损失 12.5% Prefill 容量 |
| **故障表现** | 如果 Proxy 使用 `disagg_proxy_demo.py`，失败实例被自动移除，剩余 7P8D 继续服务。如果使用 `mooncake_connector_proxy.py`，无自动移除，Round-Robin 会持续路由到失败实例 → 每 8 个请求有 1 个失败 |
| **恢复策略** | K8s 自动重启 Pod（restartPolicy: Always），重启后需重新注册到 Bootstrap Server |

### 5.2 单个 D 实例崩溃

| 维度 | 描述 |
|------|------|
| **故障描述** | 8 个 Decode 实例中某一个崩溃 |
| **影响范围** | 该 D 实例正在生成的请求丢失 |
| **影响程度** | 🟡 **中等** — 损失 12.5% Decode 容量 |
| **同 5.1** | Proxy 行为决定是自动降级还是持续失败 |

### 5.3 同一副本的 P 和 D 同时崩溃

| 维度 | 描述 |
|------|------|
| **故障描述** | 同一副本的 P 和 D 因共享基础设施故障（如机架断电）同时崩溃 |
| **影响范围** | 该副本完全不可用 |
| **影响程度** | 🟡 **中等** — 损失 12.5% 全链路容量 |
| **恢复策略** | K8s 自动重启两个 Pod。但 P 端的 Bootstrap Server 需要先就绪，D 端才能连接 |

### 5.4 单个 P/D 实例内部错误（Worker errored）

| 维度 | 描述 |
|------|------|
| **故障描述** | 实例未崩溃但 `engine_client` 进入 errored 状态 |
| **影响程度** | 🔴 **严重** — 该实例不再接受新请求，但 Proxy 不感知，持续路由 → 12.5% 请求失败 |
| **代码位置** | `serving.py:113-114` (dead_error) |
| **恢复策略** | 需重启该实例 |

## 6. 跨副本 KV Cache 共享故障

> 这是 8 副本架构特有的故障类别。MooncakeStoreConnector 的 PoolKey 不含 `dp_rank`，任何 P 的 KV 可被任何 D 加载。

### 6.1 Store 中的 KV Cache 数据损坏

| 维度 | 描述 |
|------|------|
| **故障描述** | 某个 P 实例写入损坏的 KV Cache 数据到 Store，由于跨副本共享，**其他副本的 D 实例也可能读到损坏数据** |
| **影响范围** | 可能波及多个副本的 Decode 质量 |
| **影响程度** | 🔴 **严重** — 损坏数据通过共享 Store 传播到其他副本 |
| **故障表现** | 多个 D 实例输出乱码或错误结果 |
| **代码位置** | `store/worker.py:846-903` (batch_get)，`_invalid_block_ids` 机制可检测部分错误 |
| **恢复策略** | `kv_load_failure_policy="recompute"` 可检测并重计算损坏 block。但需所有 D 实例都启用此策略 |

### 6.2 Store 反压导致多副本写入失败

| 维度 | 描述 |
|------|------|
| **故障描述** | Store 磁盘/内存不足，触发反压（`MOONCAKE_NO_AVAILABLE_HANDLE`），8 个 P 实例的写入同时受影响 |
| **影响程度** | 🔴 **严重** — 全部 P 实例的 KV Cache 无法存储 |
| **代码位置** | `store/worker.py:647-701` (backpressure) |
| **级联效应** | 后续所有 D 实例无法命中 Cache → 全量重计算 → 推理延迟飙升 |

### 6.3 跨副本 Hash 冲突

| 维度 | 描述 |
|------|------|
| **故障描述** | 不同 P 实例对不同内容计算出相同 chunk_hash（极端情况） |
| **影响范围** | D 实例加载到错误的 KV Cache |
| **影响程度** | 🟡 **中等** — 概率极低但影响严重 |
| **前置条件** | `PYTHONHASHSESEED` 未统一设置 |

### 6.4 PoolKey 中的 group_id 不一致导致 Cache Miss

| 维度 | 描述 |
|------|------|
| **故障描述** | 不同副本的 KV Cache group 配置不一致，导致相同的 block hash 生成不同的 PoolKey |
| **影响程度** | 🟡 **中等** — 跨副本 Cache 命中率降低，但不影响正确性 |
| **恢复策略** | 确保所有副本使用一致的模型配置和 `PYTHONHASHSEED=0` |

### 6.5 P2P 模式下跨副本路由错误

| 维度 | 描述 |
|------|------|
| **故障描述** | Proxy 将请求路由到 P-3 做预填充，但将 Decode 路由到 D-5。P2P 模式下 D-5 只能从其配对的 P-5 加载 KV，无法从 P-3 获取 |
| **影响程度** | 🔴 **严重** — 请求失败（P2P 模式下跨副本不共享 KV） |
| **代码位置** | `mooncake_connector_proxy.py:283-312` (kv_transfer_params 中包含 remote_engine_id 和 remote_bootstrap_addr) |
| **恢复策略** | 确保 Proxy 正确传递 P 端的 engine_id 给 D 端。当前代码已实现，但依赖 Proxy 正确路由 |

## 7. Proxy 代理故障

> Proxy 是所有 8P8D 实例的统一入口，其故障影响全部副本。

### 7.1 Proxy 进程崩溃

| 维度 | 描述 |
|------|------|
| **故障描述** | Proxy 进程崩溃 |
| **影响范围** | 全部 8P8D 实例无法接收新请求 |
| **影响程度** | 🔴🔴🔴 **灾难级** — 系统对外完全不可用（即使 16 个推理实例都正常） |
| **恢复策略** | K8s 自动重启 Proxy Pod。需确保 Proxy 配置了健康检查和合理的 restartPolicy |

### 7.2 Proxy Round-Robin 路由到已故障实例

| 维度 | 描述 |
|------|------|
| **故障描述** | 某个 P 或 D 实例已故障，但 Proxy 不知道（`mooncake_connector_proxy.py` 无自动移除逻辑），持续将 1/8 的请求路由到故障实例 |
| **影响范围** | 每 8 个请求中有 1 个失败 |
| **影响程度** | 🔴 **严重** — 持续 12.5% 的请求失败 |
| **代码位置** | `mooncake_connector_proxy.py` 无实例移除逻辑；`disagg_proxy_demo.py:327-333` 有移除逻辑 |
| **恢复策略** | 使用 `disagg_proxy_demo.py` 版本可自动移除。或为 Proxy 增加健康检查机制 |

### 7.3 Proxy 无法发现 P 端 Bootstrap 信息

| 维度 | 描述 |
|------|------|
| **故障描述** | Proxy 启动时查询 P 端 Bootstrap Server 失败，无法获取 engine_id |
| **影响程度** | 🟡 **中等** — 该 P 实例不会被纳入路由 |
| **代码位置** | `mooncake_connector_proxy.py:38-63` (get_prefiller_info) |
| **恢复策略** | Proxy 在启动时轮询 P 的 `/health` 直到就绪。但**不支持运行时动态发现新实例** |

### 7.4 Prefill 失败但 Proxy 不感知

| 维度 | 描述 |
|------|------|
| **故障描述** | Proxy 将 Prefill 请求以 fire-and-forget 方式发送（`asyncio.create_task`），P 端计算失败但 Proxy 不知道 |
| **影响范围** | 后续 Decode 请求必然失败（找不到 KV Cache） |
| **影响程度** | 🟡 **中等** — 单请求失败 |
| **代码位置** | `mooncake_connector_proxy.py:327-331` |
| **恢复策略** | 需客户端重试。增加 Prefill 结果确认机制可避免此问题 |

### 7.5 Proxy 成为性能瓶颈

| 维度 | 描述 |
|------|------|
| **故障描述** | 单个 Proxy 处理 8P8D 的全部流量，高并发下成为瓶颈 |
| **影响程度** | 🟡 **中等** — 延迟升高 |
| **恢复策略** | 部署多 Proxy 实例 + 负载均衡 |
