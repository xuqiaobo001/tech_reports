# 华为云 ModelArts NPU "用户输入引发"芯片故障深度分析

> 基于华为云 ModelArts 官方文档和昇腾社区资料，深度分析故障码 80C98002 / 80CB8002 所代表的"用户输入引发"芯片故障的含义、触发场景、与硬件故障的区别，以及平台为何对此类故障采用不同的恢复策略（不隔离节点）。

---

## 一、问题背景

在 ModelArts 训练作业故障恢复机制中，NPU 原地恢复的降级策略有一条特殊规则：

> "一次训练过程中，同一节点同一芯片 24 小时内连续 3 次出现相同故障码，且是 **80C98002** 或 **80CB8002** 这类由用户输入引发的芯片故障，此时**不隔离节点**，只执行重调度。"

这引出两个关键问题：
1. **"用户输入"具体指什么？** 是用户在控制台的操作，还是训练代码/数据？
2. **为什么不隔离节点？** 其他硬件故障都会隔离节点，为什么这类故障不隔离？

---

## 二、"用户输入"的准确定义

**"用户输入"不是指用户在控制台的交互操作**，而是指**用户提交的训练代码中的算子（Operator）或训练数据**触发了 NPU 芯片异常。

| 故障码 | 分类 | 本质 | 来源 |
|--------|------|------|------|
| **80C98002** | 用户侧引发 | 非硬件故障 | 训练代码中的算子或数据 |
| **80CB8002** | 用户侧引发 | 非硬件故障 | 训练代码中的算子或数据 |

这两个故障码的特征是：**换一个节点跑同样的代码和数据，还会出现同样的错误**。这说明问题不在硬件，而在用户的训练代码或数据中。

---

## 三、"用户输入"触发的具体场景

### 3.1 算子异常（最主要原因）

用户训练代码中使用的 AI 算子（Operator）存在问题，导致 NPU 芯片在执行计算时触发异常。

| 场景 | 说明 | 触发示例 |
|------|------|---------|
| **自定义算子 bug** | 用户自己开发的算子存在内存访问越界、非法地址等 | 自定义 CUDA/NPU 算子中 buffer 越界读写 |
| **不支持的算子参数** | 使用了当前 CANN 版本不支持的参数组合 | 某些高维 Shape 在特定 CANN 版本下不支持 |
| **算子内部溢出** | 计算结果超出 NPU 数据类型表示范围 | float16 的最大值约 65504，超出即溢出 |
| **CANN 版本不兼容** | 训练代码使用的算子接口与运行环境 CANN 版本不匹配 | 使用了 CANN 8.0 的算子但环境是 CANN 7.0 |
| **算子融合异常** | 图编译阶段算子融合策略导致底层计算异常 | 特定算子组合在融合后产生非预期行为 |

### 3.2 输入数据异常

用户输入到模型的训练数据触发了 NPU 芯片错误。

| 场景 | 说明 | 触发示例 |
|------|------|---------|
| **NaN / Inf 值** | 训练数据或中间结果中包含 NaN 或 Inf | 数据预处理异常产生 NaN，传入 Softmax 算子 |
| **数值溢出** | 输入值超出算子的合法数值范围 | Logits 值过大（如 >1e4），Softmax 前未做裁剪 |
| **维度不匹配** | Tensor 的 shape 与算子期望不一致 | 传入 [B, L, H] 但算子期望 [B, H, L] |
| **异常大的值** | 梯度爆炸导致数值超出芯片处理范围 | 学习率过大导致梯度值达到 1e38+ |
| **数据类型错误** | 传入的数据类型与算子预期不匹配 | 算子期望 float16 但收到 int32 |

### 3.3 典型触发链路

```
用户提交训练代码到 ModelArts
  │
  ├─ 路径 A：自定义算子有 bug
  │    └─ 算子执行时访问非法内存地址
  │         └─ NPU 芯片触发故障码 80C98002
  │              └─ 原地恢复尝试自愈
  │                   └─ 自愈成功但代码不变 → 下次还会触发
  │                        └─ 24h 内连续 3 次 → 不隔离节点 → Job 重调度
  │
  ├─ 路径 B：训练数据包含 NaN/Inf
  │    └─ NaN 传入下游算子（如 LayerNorm、Softmax）
  │         └─ NPU 芯片在处理 NaN 时触发异常
  │              └─ 故障码 80C98002
  │                   └─ 换节点后同样的数据 → 同样出错
  │
  └─ 路径 C：梯度爆炸导致数值溢出
       └─ loss 值变为 Inf
            └─ 反向传播时算子处理 Inf 触发芯片异常
                 └─ 故障码 80CB8002
                      └─ 裁剪梯度后恢复正常
```

## 四、用户输入故障 vs 硬件故障的区别

### 4.1 核心差异

| 维度 | 硬件故障 | 用户输入故障（80C98002/80CB8002） |
|------|---------|-------------------------------|
| **根因** | 芯片物理损坏、HBM 坏块等 | 代码/数据问题 |
| **可复现性** | 特定节点复现 | **换任何节点都复现** |
| **自愈可能性** | 部分可自愈（如 HBM 多比特 ECC） | 自愈后代码不变还会触发 |
| **隔离节点** | **是**（防止其他作业调度到故障节点） | **否**（节点没问题，隔离无意义） |
| **恢复策略** | 隔离式 Job 重调度 | 无条件 Job 重调度（不隔离） |
| **根本解决** | 换硬件 | **用户修复代码或数据** |

### 4.2 为什么不隔离节点

```
硬件故障的处理逻辑：
┌─────────────────────────────────────────────────────────┐
│  节点 A 的 NPU 芯片 HBM 有坏块                            │
│    → 这个节点确实坏了                                      │
│    → 换到节点 B 可以正常训练                                │
│    → 所以要隔离节点 A（打 K8s taint 污点）                  │
│    → 防止其他作业被调度到这个坏节点                          │
│    → 通知运维人员修复/更换硬件                               │
└─────────────────────────────────────────────────────────┘

用户输入故障的处理逻辑：
┌─────────────────────────────────────────────────────────┐
│  节点 A 上用户的算子有 bug 导致 80C98002                    │
│    → 节点 A 的硬件本身是好的                                │
│    → 换到节点 B 跑同样的代码 → 还会出错                      │
│    → 隔离节点 A 没有意义（问题不在节点）                      │
│    → 只做 Job 重调度（换节点重试）                           │
│    → 如果连续 3 次都复现 → 确认是代码问题 → 作业终止          │
│    → 提示用户自行排查代码/数据                               │
└─────────────────────────────────────────────────────────┘
```

### 4.3 连续 3 次的设计意图

```
第一次触发 80C98002：
  → 可能是偶发问题，尝试重调度恢复

第二次触发（同一芯片同一故障码）：
  → 仍然可能是偶发，继续尝试

第三次触发（24h 内同一芯片同一故障码）：
  → 连续 3 次同样的错误 → 不太可能是偶发
  → 判定是用户侧问题（代码或数据）
  → 不隔离节点（节点是好的）
  → 执行 Job 重调度，但此时期望用户注意到并修复

如果用户未修复，重调度后还会再次触发：
  → 超过最大重启次数 → 作业终止为失败
  → 用户查看日志发现故障码 80C98002/80CB8002
  → 根据排查建议修复代码或数据
```

## 五、故障码分类体系

昇腾 NPU 芯片故障按严重程度和来源分为四个级别：

| 级别 | 严重程度 | 处理方式 | 是否可自愈 | 典型故障 |
|------|---------|---------|-----------|---------|
| **提示** | 最低 | 不需要处理 | — | 信息性告警 |
| **次要** | 低 | 可自动恢复 | 是（原地恢复） | 部分 ECC 纠错 |
| **重要** | 中 | 可自动恢复 | 是（原地恢复） | HBM 多比特 ECC |
| **紧急** | 最高 | 无法自愈 | 否 | 芯片物理损坏 |

**80C98002 / 80CB8002 属于"重要"级别**，芯片可以自愈恢复，但因为根因在用户代码/数据，自愈后还会复现。

## 六、排查建议

### 6.1 按优先级排查

| 优先级 | 排查项 | 具体操作 |
|--------|--------|---------|
| **P0** | **CANN 版本** | 检查当前 CANN 版本是否为推荐或最新商用版本，查看版本配套关系表 |
| **P0** | **算子实现** | 排查使用的算子是否存在已知问题，特别是自定义算子 |
| **P1** | **输入数据** | 在训练代码中加入数据校验，检测 NaN/Inf/异常大值 |
| **P1** | **梯度裁剪** | 添加 `torch.nn.utils.clip_grad_norm_` 防止梯度爆炸 |
| **P2** | **混合精度** | 检查 float16 是否导致数值溢出，考虑使用 AMP（自动混合精度） |
| **P2** | **错误码查询** | 使用华为[错误码查询工具](https://info.support.huawei.com/computing/tools/om-info-query)获取详细定义 |

### 6.2 常见修复方法

#### 修复 NaN/Inf 问题

```python
import torch

# 在训练循环中添加数据校验
def check_tensor_health(tensor, name="tensor"):
    if torch.isnan(tensor).any():
        print(f"WARNING: {name} contains NaN!")
    if torch.isinf(tensor).any():
        print(f"WARNING: {name} contains Inf!")
    if tensor.abs().max() > 1e6:
        print(f"WARNING: {name} has abnormally large values: max={tensor.abs().max()}")

# 添加梯度裁剪
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

# 使用 AMP 自动混合精度
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast():
    output = model(input)
    loss = criterion(output, target)
scaler.scale(loss).backward()
scaler.unscale_(optimizer)
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
scaler.step(optimizer)
scaler.update()
```

## 七、故障恢复策略对比总结

| 故障类型 | 故障码示例 | 恢复策略 | 是否隔离节点 | 原因 |
|----------|-----------|---------|-------------|------|
| 可自愈芯片故障 | HBM ECC 等 | 原地恢复 | 否 | 芯片自愈后可继续使用 |
| 可自愈故障反复出现 | 同码 24h 3 次 | 隔离式 Job 重调度 | **是** | 可能是硬件隐患 |
| **用户输入引发** | **80C98002 / 80CB8002** | **无条件 Job 重调度** | **否** | **问题在代码，不在硬件** |
| 不可自愈硬件故障 | 芯片损坏 | 隔离式 Job 重调度 | 是 | 硬件确有故障 |
| 软件异常 | 退出码≠0 | 无条件 Job 重调度 | 否 | 非硬件问题 |

## 八、总结

| 要点 | 说明 |
|------|------|
| **"用户输入"是什么** | 不是控制台操作，而是训练代码中的**算子异常**和**数据异常**（NaN/Inf/溢出等） |
| **典型故障码** | 80C98002、80CB8002 |
| **为什么不隔离节点** | 节点硬件本身没问题，换节点还会复现，隔离无意义 |
| **根本解决方式** | 用户修复代码或数据（排查 CANN 版本、算子实现、输入数据） |
| **平台如何处理** | 先尝试原地恢复自愈，连续 3 次后判定为用户侧问题，不隔离节点直接 Job 重调度 |
| **如何避免** | 使用推荐 CANN 版本、添加数据校验和梯度裁剪、避免自定义算子 bug |
