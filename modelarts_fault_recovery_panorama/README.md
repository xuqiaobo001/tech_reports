华为云 ModelArts（魔坊）是面向开发者的全栈 AI 开发平台，提供从数据准备、模型训练、推理部署到强化学习后训练的端到端能力。

## 二、故障恢复体系全景图

ModelArts 为模型训练构建了 **三级恢复 + 五大策略 + 两层前置检测** 的完整故障恢复体系：

```
┌──────────────────────────────────────────────────────────────────────┐
│                ModelArts 训练作业故障恢复全景图                        │
│                                                                      │
│  ┌───── 前置检测层 ──────────────────────────────────────────────┐   │
│  │  环境预检测：DNS / 磁盘 / ulimit / GPU                        │   │
│  │  硬件周期性检查：NPU 芯片健康状态持续监控                        │   │
│  └───────────────────────────────────────────────────────────────┘   │
│                              ↓ 通过                                  │
│  ┌───── 第一级：进程级恢复（容器保留，仅重启进程）────────────┐   │
│  │  ① NPU 原地恢复 — 芯片可自愈故障（HBM 多比特 ECC 等）       │   │
│  │  ② 卡死重启   — 平台检测到训练作业卡死                      │   │
│  └───────────────────────────────────────────────────────────────┘   │
│                           ↓ 降级                                     │
│  ┌───── 第二级：POD 级恢复（仅重建故障 Pod，保留正常 Pod）──┐   │
│  │  ③ Pod 重调度 — NPU 芯片不可自愈故障 / 节点故障              │   │
│  └───────────────────────────────────────────────────────────────┘   │
│                           ↓ 降级                                     │
│  ┌───── 第三级：Job 级恢复（删除重建整个 Job）───────────────┐   │
│  │  ④ 隔离式 Job 重调度 — 先隔离故障节点，再重建整个 Job        │   │
│  │  ⑤ 无条件 Job 重调度 — 退出码≠0 即重建（软件/网络故障）      │   │
│  └───────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  ┌───── 基础支撑 ──────────────────────────────────────────────┐   │
│  │  断点续训（Checkpoint 机制）：定期保存模型权重 + 优化器状态    │   │
│  │  环境变量：MA_SCHEDULE_CNT / MA_PROC_START_CNT 辅助可重入     │   │
│  └───────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────┘
```

## 三、前置检测：容错检查机制

容错检查是故障恢复的第一道防线，包含 **环境预检测** 和 **硬件周期性检查** 两个阶段：

### 3.1 环境预检测

训练作业启动前自动执行的环境检查：

| 检测项 | 日志关键字 | 执行条件 | 通过标准 |
|--------|-----------|---------|---------|
| 域名解析 | `dns` | 始终执行 | Volcano 容器域名解析成功 |
| 根目录磁盘空间 | `disk-size root` | 始终执行 | >32GB |
| 共享内存空间 | `disk-size shm` | 始终执行 | >1GB |
| 缓存目录空间 | `disk-size cache` | 始终执行 | >32GB |
| ulimit 限制检查 | `ulimit` | 使用 IB 网络时 | max locked memory>16000, open files>1000000 等 |
| GPU 可用性 | `gpu-check` | GPU + v2 引擎 | 检测到 GPU |

### 3.2 硬件周期性检查

训练运行过程中持续监控 NPU 芯片健康状态。

### 3.3 容错检查四大场景

```
场景一：环境预检失败 + 硬件故障
  → 隔离所有故障节点，重新下发训练作业

场景二：环境预检失败 + 硬件正常
  → 随机再分配节点，重新下发训练作业

场景三：预检通过 + 运行中硬件故障 + 业务异常退出
  → 隔离故障节点，重新下发训练作业

场景四：预检通过 + 硬件正常 + 业务代码异常
  → 以失败状态结束作业（不做自动恢复）
```

### 3.4 隔离后处理

- 系统自动在新的计算节点上重建训练作业
- 资源池紧张时以**第一优先级排队**
- 排队超 30 分钟自动退出（建议购买专属资源池补充节点）
- 专属资源池的故障节点会被自动剔除并补充健康节点

## 四、第一级恢复：进程级恢复

### 4.1 NPU 原地恢复

**原理**：部分 NPU 芯片故障可通过系统修复或复位自愈。对可自愈故障，系统在原容器中重启训练进程，**不销毁容器、不重新调度资源**。

```
┌─────────────────────────────────────────────────────────┐
│              NPU 原地恢复流程                              │
│                                                           │
│  1. 检测到 NPU 芯片可自愈故障（如 HBM 多比特 ECC）         │
│     │                                                     │
│     ▼                                                     │
│  2. 强制停止容器中的用户进程                               │
│     │   容器本身不销毁，保留运行环境                        │
│     ▼                                                     │
│  3. 尝试 NPU 芯片自愈                                     │
│     │   系统修复/复位芯片                                  │
│     ▼                                                     │
│  4. 自愈成功？                                            │
│     ├─ 是 → 重新运行训练作业启动命令                       │
│     └─ 否 → 降级到隔离式 Job 重调度                        │
│                                                           │
│  全程：不涉及资源调度，不占用"最大重启次数"                  │
└─────────────────────────────────────────────────────────┘
```

**可自愈故障定义**：通常是故障级别为"次要"或"重要"的故障码。"提示"级不需处理，"紧急"级无法自愈。

**约束**：
- 作业需定期保存 CKPT
- 作业支持断点续训
- 作业脚本可重入（跳过数据下载/预处理，重建同名共享内存）

**降级策略**：
| 降级条件 | 降级目标 |
|----------|---------|
| 芯片自愈失败 | → 隔离式 Job 重调度 |
| 24h 内同芯片同故障码连续 3 次 | → 隔离式 Job 重调度 |
| 用户输入引发的故障（80C98002/80CB8002） | → 无条件 Job 重调度（不隔离节点） |

### 4.2 卡死重启

**原理**：当训练作业长时间无 IO 变化时，平台检测到卡死状态，强制停止用户进程后在原容器中重启。

**卡死检测规则**：
- 环境变量 `MA_HANG_DETECT_TIME=30`（默认 30 分钟无 IO 变化判定卡死）
- 检测分为**单实例检测**和**全实例检测**
- 仅支持 GPU 和 NPU 资源类型

```
┌─────────────────────────────────────────────────────────┐
│              卡死重启流程                                  │
│                                                           │
│  1. 协程周期性监控进程状态和资源利用率                      │
│     │                                                     │
│     ▼                                                     │
│  2. 检测到 IO 无变化超过阈值（默认 30min）                 │
│     │                                                     │
│     ▼                                                     │
│  3. 强制停止容器中的用户进程                               │
│     │   容器本身不销毁，保留运行环境                        │
│     ▼                                                     │
│  4. 重新运行训练作业启动命令                               │
│                                                           │
│  全程：不涉及资源调度，不占用"最大重启次数"                  │
└─────────────────────────────────────────────────────────┘
```

**约束**：
- 作业定期保存 CKPT
- 作业支持断点续训
- 脚本可重入（涉及数据下载、预处理、同名共享内存等）

**降级策略**：连续 3 次卡死重启后，作业自动终止并置为失败。

## 五、第二级恢复：Pod 重调度

**原理**：保留现有 Job 实例不变，仅隔离故障节点并重新创建故障 Pod，正常 Pod 继续运行。

```
┌─────────────────────────────────────────────────────────┐
│              Pod 重调度流程                                │
│                                                           │
│  1. 检测到节点故障或 NPU 芯片不可自愈故障                   │
│     │                                                     │
│     ▼                                                     │
│  2. 隔离故障节点                                          │
│     │   将故障节点从可用资源池中剔除                        │
│     ▼                                                     │
│  3. 仅重新创建故障 Pod                                    │
│     │   正常 Pod 保持不变，继续运行                        │
│     ▼                                                     │
│  4. 新 Pod 加入集群，恢复分布式训练                        │
│                                                           │
│  优势：恢复速度快，正常实例不受影响                         │
└─────────────────────────────────────────────────────────┘
```

**约束**：
- 作业定期保存 CKPT
- 作业支持断点续训
- 需要**健康备用机**
- 正常实例的容器环境保留，要求脚本可重入

**降级策略**：Pod 重调度失败 → 降级到无条件 Job 级重调度（节点已隔离）。

## 六、第三级恢复：Job 级恢复

### 6.1 隔离式 Job 重调度

**原理**：在无条件 Job 重调度基础上，先隔离故障节点，再删除重建整个 Job。

```
┌─────────────────────────────────────────────────────────┐
│              隔离式 Job 重调度流程                          │
│                                                           │
│  1. 检测到节点故障 / 原地恢复降级                           │
│     │                                                     │
│     ▼                                                     │
│  2. 隔离故障节点                                          │
│     │   将故障节点从资源池中永久剔除                        │
│     ▼                                                     │
│  3. 终止用户作业涉及的所有 Pod                              │
│     │                                                     │
│     ▼                                                     │
│  4. 在新的健康节点上完全重建 Job                            │
│     │   从 Checkpoint 恢复训练进度                         │
│     ▼                                                     │
│  5. 恢复正常训练                                          │
└─────────────────────────────────────────────────────────┘
```

**约束**：
- 作业定期保存 CKPT
- 作业支持断点续训
- 需要**健康备用机**

**降级策略**：无（最高级别恢复）。

### 6.2 无条件 Job 重调度

**原理**：不判断是否为硬件故障，只要作业异常结束且退出码≠0，就完全重建 Job。

```
┌─────────────────────────────────────────────────────────┐
│              无条件 Job 重调度流程                          │
│                                                           │
│  1. 作业异常结束，退出码 ≠ 0                               │
│     │                                                     │
│     ▼                                                     │
│  2. 终止用户作业涉及的所有 Pod                              │
│     │   不隔离任何节点（因为可能不是硬件故障）               │
│     ▼                                                     │
│  3. 完全重建 Job                                          │
│     │   在原节点或其他节点上重新下发                        │
│     ▼                                                     │
│  4. 从 Checkpoint 恢复训练                                 │
│                                                           │
│  优势：覆盖软件故障和网络波动等非硬件问题                    │
└─────────────────────────────────────────────────────────┘
```

**触发场景**：
- 原地恢复中用户输入引发的降级
- 作业失败中断且退出码≠0
- Pod 重调度失败降级

**约束**：
- 作业定期保存 CKPT
- 作业支持断点续训
- 作业异常时业务能够中断退出（退出码≠0）
- **无需备用机**

**降级策略**：连续 3 次触发后，第 4 次且中间未发生节点/芯片故障，系统判定用户代码异常，作业终止为失败。

**注意**：作业被驱逐的场景不支持触发无条件 Job 重调度，作业状态将变为失败。

## 八、配置方式

### 8.1 控制台配置

在创建训练作业时，**步骤六：容错与恢复** 提供以下开关：

| 配置项 | 包含策略 | 说明 |
|--------|---------|------|
| **自动重启** | 原地恢复 + 隔离式 Job 重调度 | 可设置最大重启次数（1~128） |
| **无条件自动重启** | 无条件 Job 重调度 | 连续最多 3 次 |
| **作业卡死重启** | 卡死重启 | 不占用最大重启次数 |

### 8.2 API 配置

```json
{
    "kind": "job",
    "metadata": {
        "annotations": {
            "fault-tolerance/job-retry-num": "8",
            "fault-tolerance/job-unconditional-retry": "true",
            "fault-tolerance/hang-retry": "true",
            "fault-tolerance/pod-retry-num": "3"
        }
    }
}
```

| 参数 | 说明 | 范围 |
|------|------|------|
| `fault-tolerance/job-retry-num` | 自动重启次数 | 1~128 |
| `fault-tolerance/job-unconditional-retry` | 无条件重启 | true/false |
| `fault-tolerance/hang-retry` | 卡死重启 | true/false |
| `fault-tolerance/pod-retry-num` | Pod 重调度次数 | 1~128 |

### 8.3 关键环境变量

| 变量名 | 说明 | 用途 |
|--------|------|------|
| `MA_SCHEDULE_CNT` | Pod 被调度的次数（新作业=1，每次重调度+1） | 判断是否发生过重调度恢复 |
| `MA_PROC_START_CNT` | 当前 Pod 内用户脚本执行次数（原地恢复/卡死重启后+1） | 判断是否需要跳过数据加载/重建共享内存 |
| `MA_HANG_DETECT_TIME` | 卡死检测超时时间（默认 30 分钟） | 自定义卡死检测灵敏度 |
| `MA_FAILOVER_TERMINATION_GRACE_PERIOD_SECONDS` | 异步卷卸载延迟（默认 -1） | SFS Turbo 场景建议设为 10，加速重调度 |

## 九、断点续训（Checkpoint 机制）

断点续训是所有故障恢复策略的**基础前提**。不配置断点续训，恢复后训练将从零开始。

### 9.1 工作原理

```
┌─────────────────────────────────────────────────────────┐
│              Checkpoint 断点续训机制                       │
│                                                           │
│  训练运行中：                                              │
│     定期保存 → 模型权重（net state_dict）                  │
│              → 优化器状态（optimizer state_dict）           │
│              → 调度器状态（scheduler state_dict）           │
│              → Epoch/Step 信息                             │
│              → 随机数生成器状态                             │
│     存储到 → OBS / SFS Turbo（持久化存储）                 │
│                                                           │
│  故障恢复后：                                              │
│     1. 新作业启动前自动下载 Checkpoint 到本地               │
│     2. 训练脚本检测到已有 Checkpoint                       │
│     3. 加载最新的 Checkpoint 初始化训练状态                 │
│     4. 从中断位置继续训练                                   │
└─────────────────────────────────────────────────────────┘
```

### 9.2 PyTorch 代码适配示例

```python
import os
import torch

def save_checkpoint(model, optimizer, epoch, path):
    """定期保存 Checkpoint"""
    checkpoint = {
        "net": model.state_dict(),
        "optimizer": optimizer.state_dict(),
        "epoch": epoch
    }
    torch.save(checkpoint, os.path.join(path, f'ckpt_{epoch}.pth'))

def load_checkpoint(model, optimizer, path):
    """加载最新 Checkpoint 实现断点续训"""
    if os.path.exists(path) and os.listdir(path):
        ckpts = sorted([f for f in os.listdir(path) if f.endswith('.pth')])
        if ckpts:
            latest = os.path.join(path, ckpts[-1])
            checkpoint = torch.load(latest)
            model.load_state_dict(checkpoint['net'])
            optimizer.load_state_dict(checkpoint['optimizer'])
            return checkpoint['epoch']
    return 0  # 从头开始训练

# 使用方式
train_url = args.train_url  # ModelArts 训练输出路径
start_epoch = load_checkpoint(model, optimizer, train_url)

for epoch in range(start_epoch + 1, total_epochs):
    train_one_epoch(model, optimizer, ...)
    save_checkpoint(model, optimizer, epoch, train_url)
```

### 9.3 RL 框架断点续训配置

**VeRL 框架**：
```yaml
backend_config:
  trainer:
    resume_mode: resume_path     # 指定断点 / latest_checkpoint
    resume_path: /path/to/ckpt   # Checkpoint 路径
```

**Llama-Factory 框架**：
1. 获取训练输出目录中的 Checkpoint 路径
2. 修改训练配置 YAML 的断点续训参数
3. 重新启动训练任务

**MindSpeed-RL / MindSpeed-LLM / MindSpeed-MM**：
- 确认已保存的权重文件存在
- 修改训练配置 YAML 中的断点续训配置
- 重新启动训练任务

## 十、强化学习训练能力与故障恢复

### 10.1 RL 训练框架

ModelArts 通过 **AscendFactory** 方案集成两大 RL 框架：

| 框架 | 定位 | 支持算法 | 核心特性 |
|------|------|---------|---------|
| **VeRL** | 开源后训练标准框架 | GRPO / PPO / DAPO | 异步 Rollout、训推分离、LoRA 微调、多模态 RL |
| **MindSpeed-RL** | 昇腾原生 RL 框架 | GRPO / PPO | DP 负载均衡、动态 Batch Size、长序列 64K |

### 10.2 支持的 RL 训练场景

| 模型 | 框架 | 算法 | 序列长度 | 特殊能力 |
|------|------|------|---------|---------|
| Qwen2.5 系列 | VeRL / MindSpeed-RL | GRPO/PPO | 标准 | 异步 Rollout |
| Qwen3-30B-A3B | VeRL / MindSpeed-RL | GRPO | 64K 长序列 | DP 负载均衡 |
| Qwen3-VL-30B-A3B | VeRL | GRPO | 标准 | 多模态 RL |
| Qwen2.5-VL-72B | VeRL | DAPO | 标准 | 大模型 RL |

### 10.3 RL 训练故障恢复的特殊考虑

强化学习训练相比普通 SFT 训练有以下特殊之处：

```
┌─────────────────────────────────────────────────────────┐
│          RL 训练故障恢复特殊考虑                            │
│                                                           │
│  1. 多角色协作（Actor / Critic / Reward / Ref）            │
│     → 各角色需独立保存和恢复 Checkpoint                    │
│     → 恢复时需保证各角色状态一致性                          │
│                                                           │
│  2. 训推分离架构                                           │
│     → 训练节点和推理节点可能分别故障                        │
│     → 需要分别处理训练端和推理端的恢复                      │
│                                                           │
│  3. Experience Buffer                                     │
│     → 在线采集的样本数据可能丢失                            │
│     → 恢复后需要重新采样部分数据                            │
│                                                           │
│  4. KL 散度约束                                           │
│     → 恢复后需确保策略更新不违反 KL 约束                   │
│     → 需要保存 Reference Model 的状态                      │
│                                                           │
│  5. 分布式通信更复杂                                       │
│     → Actor-Critic 间的梯度同步                            │
│     → 恢复后需重建通信拓扑                                 │
└─────────────────────────────────────────────────────────┘
```

**RL 断点续训需要保存的内容**：

| 组件 | 保存内容 |
|------|---------|
| Actor 模型 | 模型权重 + 优化器状态 + 调度器状态 |
| Critic 模型 | 模型权重 + 优化器状态 + 调度器状态 |
| Reward Model | 模型权重（如有） |
| Reference Model | 原始模型权重（用于 KL 约束） |
| Tokenizer | 词表和配置文件 |
| 训练状态 | 当前 Step/Epoch、全局 Batch 计数 |

## 十二、故障恢复策略选型决策树

```
┌──────────────────────────────────────────────────────────────┐
│              故障恢复策略选型决策树                             │
│                                                                │
│  是否需要故障自动恢复？                                         │
│    ├─ 否 → 不开启任何恢复策略                                   │

│              │                                                  │
│              ├─ 否 → 基本配置：自动重启（1~3次）                 │
│              │                                                  │
│              └─ 是 → 硬件类型？                                  │
│                    │                                            │
│                    ├─ NPU → 完整配置：                           │
│                    │    ├─ 自动重启（8~128次）                   │
│                    │    ├─ 无条件自动重启（开启）                 │
│                    │    ├─ 作业卡死重启（开启）                   │
│                    │    └─ Pod 重调度（3次）                     │
│                    │                                            │
│                    └─ GPU → 基础配置：                           │
│                         ├─ 自动重启（3~8次）                     │
│                         └─ 作业卡死重启（开启）                   │
│                                                                │
│  所有场景必须：                                                 │
│    ✅ 定期保存 Checkpoint                                      │
│    ✅ 代码适配断点续训                                          │
│    ✅ 脚本可重入（利用环境变量 MA_SCHEDULE_CNT 等）              │
└──────────────────────────────────────────────────────────────┘
```

## 十三、最佳实践总结

### 13.1 通用训练作业

| 实践项 | 建议 |
|--------|------|
| Checkpoint 保存频率 | 每 N Step 保存一次（N 根据训练时长调整，建议 100~1000） |
| Checkpoint 保存数量 | 保留最近 3~5 个，避免存储空间溢出 |
| 存储选择 | 使用 SFS Turbo（低延迟）或 OBS（低成本） |
| 自动重启次数 | NPU 长时训练建议 8~128 次 |
| 卡死检测阈值 | 根据业务特点调整 `MA_HANG_DETECT_TIME` |

### 13.2 RL 训练作业

| 实践项 | 建议 |
|--------|------|
| 各角色独立 CKPT | Actor / Critic / Reward Model 分别保存 |
| 训推分离场景 | 训练端和推理端分别配置故障恢复 |
| 异步 Rollout | 开启异步模式提高资源利用率 |
| 动态 Batch Size | 开启 MindSpeed-RL 的 Dynamic Batch Size |

### 13.3 专属资源池管理

| 实践项 | 建议 |
|--------|------|
| 备用节点 | 保留 10%~20% 的冗余节点用于故障恢复 |
| 节点排水 | 扩缩容时开启节点排水（Graceful Drain） |
| 驱动升级 | 定期升级 NPU 驱动以修复已知芯片问题 |
| 节点故障检测 | 安装 ModelArts Node Agent 插件实现主动检测 |

| 维度 | ① 原地恢复 | ② 卡死重启 | ③ Pod 重调度 | ④ 隔离式 Job 重调度 | ⑤ 无条件 Job 重调度 |
